## Четыре сквозных маршрута и разрывы

1. **Item/форма → атака → чат/защита → урон/броня → ресурс.** Item row вызывает Actor.useItem, Weapon-ветка — weaponAttack; getItemAttack читает поля и опции. После prompt и построения payload код выбирает rollOnlyDmg или typed AttackMessage. В чате отдельно выбирают damage/defense; выбранная цель не обязана быть отправителем. DamageMessage содержит свой тип properties; applyDamageFromMessage выбирает ресурс/флаги, затем shield/location/SP/resistance/tempHP/resource. Ни создание сообщения, ни наличие обратной связи не обещают достижение конечной записи при исключении.
2. **Crit action → Item → rest/heal/treat.** Три crit action независимы: основное повреждение, бонус и Item травмы. applyCritWound фильтрует pack.index, разрешает UUID, передаёт addItem. addItem сравнивает имя/тип, не новый механизм повторных травм. При отдыхе сначала ожидается Actor.update, затем запускаются heal всех CriticalWound. Treatment и порог имеют разные guards; deadly запрещает автоматический treat. В treat загрузка followUp ожидается, создание нового Item и удаление старого — нет; успешное сохранение не подтверждено графом.
3. **Combat → damage/heal.** Hook реагирует на updateCombat; regeneration и effects запускаются без общей очереди ожидания. У regeneration есть monster/nonzero/!dead, у periodic heal — собственный positive amount/positive delta. Periodic damage wrapper не ожидает внутренний applyDamage и не передаёт объявленный type в payload. ADD/SchemaField и prepared-объект могут остановить путь раньше числового урона. Полноценная симуляция раунда здесь не выполнялась.
4. **Consume → ресурс/статус/эффект + списание.** consume вычисляет лечение, запускает HP update, статус/удаление статуса, applySelf и сообщение. Quantity меняет вызывающий useItem/menu; consume и removeItem запускаются без ожидания. Поэтому удаление последнего Item может пересечься с поздним UUID resolution эффекта. Это граница порядка, а не утверждение о неизбежной потере эффекта. applyStatus с непустыми immunities имеет отдельную ранее описанную ошибку после toggle; её нельзя скрывать успешным downstream-поиском.
