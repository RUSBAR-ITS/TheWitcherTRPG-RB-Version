## Реестр и карточки

В реестре используется полный путь относительно корня системы. Одна строка соответствует одному исходному файлу; сортировка — по пути. Подробное описание хранится под `files/` с сохранением пути и расширения исходника и добавлением `.md`.

Пример: `module/TheWitcherTRPG.js` → `files/module/TheWitcherTRPG.js.md`. Исходные имена сохраняются, включая регистр: это обеспечивает однозначное соответствие файлов и карточек. `files/README.md` — указатель каталога, а не карточка исходного файла.

До чтения файла назначение в реестре отмечается как «Не установлено», описание — «Не подготовлено». Ссылка на карточку появляется только после создания файла описания. Совпадение имён или каталогов само по себе не служит основанием для описания назначения.

| Статус анализа | Значение |
| --- | --- |
| Не начат | Файл включён в реестр; пофайлового разбора ещё нет |
| В работе | Разбор частичный; в карточке явно перечислены ещё не исследованные участки |
| Проверено | Согласованный объём разбора завершён, карточка сверена с исходником и связями; ограничения проверки указаны |
| Требует актуализации | Изменился исходник или связанная сущность, влияющая на выводы; описание нужно пересмотреть |

Статус «Проверено» относится к описанию на указанной версии. Он не означает отсутствие ошибок в системе или проверку её запуска. Эти статусы отделены от статусов задач и проблем.

## Состав описания и связей

Каждая карточка следует [шаблону](templates/file.md) и содержит:

- Назначение файла и условия его участия в работе системы.
- Введённые сущности: классы, функции, модели, поля, настройки, константы, обработчики и другие определения.
- Основные функции и методы с существенными входами, результатами и действиями с данными.
- Используемые сущности из других файлов и внешних API, места и причины их использования.
- Известных потребителей, условия вызова и существенные изменения состояния.
- Источники доказательств, фактически выполненные проверки, непроверенные вопросы и ссылки на проблемы.

Связь записывается в едином формате: используемая сущность, файл-источник или внешний API, вид связи, место и цель использования, основание вывода. Имя сущности указывается так, как в коде; при переименовании импорта фиксируются исходное имя и локальный псевдоним. Для различения одноимённых сущностей используются путь файла и полное имя, например класс и метод.

Учитываются импорты, вызовы, наследование, регистрация классов и моделей, `Hooks`, обращения к глобальным объектам и настройкам, шаблонам, локализации и ресурсам. Регистрация обработчика, возможный вызов и выполненный при запуске вызов описываются раздельно. Неустановленный источник или динамическое разрешение помечаются явно.

Для шаблонов указываются входной контекст, используемые помощники, включаемые шаблоны и события интерфейса; для JSON — структура данных, значимые ключи, ссылки и потребители; для CSS — селекторы, подключения и связанные элементы интерфейса. Отсутствие функций у неисполняемого файла фиксируется прямо.

## Работа порциями и перекрёстная сверка

1. Перед порцией проверить коммит, рабочее дерево и применимость исследуемого среза.
2. Читать файлы порции и создавать карточки. По уточнённому с пользователем 2026-09-11 ориентиру обычный связанный блок содержит 12–16 файлов; для небольших однотипных моделей/форм допустимо до 20, для сложных центральных обработчиков — 2–5. Это ориентир, а не квота: размер зависит от методов, ветвей и внешних связей. Каждый файл разбирается целиком; работа по разделам не означает завершения карточки до проверки всех разделов.
3. Проверять определения используемых сущностей и их потребителей. Просмотр отдельного определения в соседнем файле не означает завершения его пофайлового разбора.
4. Сопоставлять карточки с кодом и между собой: исходящая связь должна согласовываться с описанием определения и известного потребителя, если эти файлы уже разобраны.
5. Проверять охват порции, пути, ссылки и статусы; записывать результаты и ограничения в [журнале](review-log.md).
6. Обновлять реестр, относящиеся к порции задачи и CHANGELOG по фактическому результату.

Для согласованной серии компедиумов .052–.061 допускаются более крупные порции однотипных JSON: 7–41 таблица либо 23–25 файлов одной группы травм. Общий структурный проход не заменяет проверку каждого документа и разбор отличий; сверки после порций сохраняются.

Граф зависимостей и полные описания процессов будут строиться позднее. Сейчас собираются проверяемые сведения для них.

## Обновление исследуемой версии

Коммит в этой основе фиксирует исходный срез. Перед продолжением сравнить его с фактически исследуемыми файлами; незакоммиченные изменения указать отдельно. Для файла вне коммита сохранить дату и контрольную сумму содержимого.

Если исходник изменился, пересмотреть карточку и зависящие от изменения выводы, отметить необходимость актуализации. В карточке записать версию, на которой проверено её содержимое; не подменять этот реквизит текущим HEAD без проверки. Обновление карточки сопровождается новой записью сверки, а не удалением свидетельства о ранее выполненной проверке.

При изменении состава перечислить добавленные, удалённые или переименованные файлы, пересмотреть реестр и ссылки, объяснить отличия от исходного среза. Изменения только внутри исключённых путей не добавляют строк в реестр. Перед сменой общего исследуемого среза согласовать её с пользователем.
