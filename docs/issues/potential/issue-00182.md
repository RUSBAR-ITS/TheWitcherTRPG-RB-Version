## Общее описание проблемы

attackFumble/defenseFumble передают message.system.attacker/defender в createResultMessage; тот вызывает ChatMessage.getSpeaker({actor}) без разрешения UUID.

## На что влияет в системе

В сообщении последствия провала отправителем может стать другой текущий персонаж, управляемый токен либо пользователь.

## Почему это проблема

attacker/defender объявлены DocumentUUIDField и содержат строки. Foundry getSpeaker распознаёт объект Actor через instanceof; UUID не подходит и запускает fallback. Получатель результата не определяется самим UUID автоматически.

## Предложение по изменению

После согласования разрешать UUID в соответствующий документ Actor и явно обрабатывать отсутствие документа; использовать его для speaker. Изменение авторства сообщения не должно подменяться изменением игровых последствий. Исправление не согласовано и не выполнялось.

## Воспроизведение и доказательства

Группа 14: реальные DataModel вернули строку Actor A; настоящий код Foundry getSpeaker с назначенным Actor B выбрал B для обоих обработчиков. При отсутствии character speaker.actor=null, alias пользователя. Контрольный getSpeaker с объектом Actor A выбрал A. Выполнены настоящие методы getSpeaker и private helpers; Actor/canvas и ChatMessage.create представлены фасадами. Сходный контракт API уже отмечен в issue-00126/00175, но здесь отдельные вызывающие места с UUID.

Подробности и пределы проверки — в [журнале сверки](../../analytics/code-audit/review-log.md#task-0003028).
