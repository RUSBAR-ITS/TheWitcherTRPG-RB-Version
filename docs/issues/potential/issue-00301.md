## Общее описание проблемы

Видимость двух команд урона проверяет только .damage-message, но callback без guard читает первую .dice-total.innerText и передаёт parseInt результата. Отсутствующее поле приводит к TypeError; нечисловой текст превращается в NaN без проверки.

## На что влияет в системе

Обработка сообщения с маркером damage-message и отсутствующим/повреждённым итогом броска, в том числе нестандартного HTML. Выбор Actor происходит раньше ошибки чтения итогового элемента.

## Почему это проблема

Условие допуска команды не проверяет данные, обязательные следующей строке. Ошибка прерывает действие, а NaN передаётся в DamageInstance. Обычная составная формула не является проблемой сама по себе: её один уже вычисленный итог поддерживается. Суммирование нескольких Roll не предполагается автоматически.

## Предложение по изменению

После согласования задать достаточные условия доступности команды и проверять наличие/конечность числового итога. Если выбирать данные из Roll вместо HTML, отдельно определить обработку нескольких бросков. Исправление не согласовано и не выполнялось.

## Воспроизведение и доказательства

Группа 08: фасад li с .damage-message, но без .dice-total, проходит visible и отклоняет callback на чтении innerText. Для .dice-total с текстом ? actual callback передал DamageInstance.damage=NaN. Контроль группы 07 с двумя DOM total7.9/99 и message.rolls99/1 взял первый parseInt7; это фиксирует источник значения, не доказывает необходимость суммирования.

Нестандартный/неполный DOM подан явно; не доказано, что штатный Foundry создаёт такое сообщение при обычном rollDamage. В реальном чате повреждённое сообщение не создавалось; дальнейшая запись NaN не выполнялась.
