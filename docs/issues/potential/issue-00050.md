## Общее описание проблемы

У временного улучшения источника start=null сохраняется при переносе на оружие. Передатчик задаёт legacy duration.combat, но не современный start; core preCreate инициализирует start для родителя Actor, тогда как получатель здесь Item. Системная ветвь требует уже заполненный start.combat.

## На что влияет в системе

Учёт срока временного улучшения на оружии при переносе источника со start=null и конечной duration. Это не утверждение об истечении всех эффектов в системе.

## Почему это проблема

В ядре Foundry 14.367 isExpiryTrackable требует непустой start. Активная временная копия на Item с start=null не допускается к регистрации отслеживания. Изображение/значение duration само по себе не запускает отсчёт.

## Предложение по изменению

Согласовать инициализацию start для эффекта на Item по владельцу Actor и текущему бою/времени. Уточнить поиск combatant через Actor владельца и проверить сроки вне боя, в бою, при переносе и повторном применении. Исправление не согласовано.

## Воспроизведение и доказательства

Настоящий BaseActiveEffect с Temporary-моделью, start=null и duration={value:3,units:'rounds'} прошёл исходный передатчик; нормализованная копия осталась start=null. В отдельной малой цепочке исполнены исходные common/core client/system _preCreate, затем core active/isTemporary/isExpiryTrackable для persisted embedded Item-эффекта: start=null, active=true, temporary=true, trackable=false. При заранее заданном start.combat отдельный вызов системного _preCreate передаёт Item в оригинальный Combat.getCombatantsByActor: combatant владельца не найден, updateSource получил {}.

**Пределы проверки:** Core /opt/foundryvtt/client/documents/active-effect.mjs:233 и 980–994; /opt/foundryvtt/client/documents/combat.mjs:170–175; /opt/foundryvtt/client/helpers/active-effect-registry.mjs проверен по add/refresh. Parent/Combat/игровые глобальные данные и запись подменены; полный клиентский lifecycle, реальный scheduler и ожидание раундов не запускались. Для обычных отслеживаемых эффектов expiryAction=delete существует и не опровергается этим сценарием.
