## Общее описание проблемы

_chooseEnhancement заранее добавляет ID в живой массив родителя, запускает отдельные update родителя и улучшения и при необходимости создаёт остаток стека без ожидания операций. Повторный ID и доступность количества не проверяются.

## На что влияет в системе

Отказ записи родителя не останавливает изменение applied/количества улучшения. Устаревший ID уже попадает в prepared-массив до ошибки. Повторное подтверждение добавляет повторные ID; выбранное улучшение с quantity=0 получает запись quantity=1.

## Почему это проблема

Данные о связи хранятся в двух Item и должны быть согласованы. Обработка не проверяет частичный результат и не восстанавливает подготовленную ссылку при отказе. Это не дубль issue-00166 об обрезке списка при подготовке листа.

## Предложение по изменению

Согласовать проверку выбранного улучшения и количества, уникальность/вместимость, порядок записи обоих документов и разделение стека. Определить поведение при отказе; changes/правила улучшений не менялись.

## Воспроизведение и доказательства

Группы 13,21: реальный callback изменил prepared enhancementItemIds, source до update остался прежним; повтор дал ['e','e']. При pending/rejected update родителя вызов update улучшения уже сделан. Выбор 'gone' добавил этот ID до TypeError. При нулевом количестве выбранного rune передано quantity=1. Стек quantity=3 создаёт копию quantity=2 с forcecreate.

Ожидаемое поведение и его основание указаны выше отдельно от факта проверки. Методика — [журнал сверки](../../analytics/code-audit/review-log.md#task-0003026).

**Пределы:** Записи представлены фасадами. Контроль с искусственно синхронным commit дал копию уже изменённого source; это не доказанный порядок нативного Document.update. Не утверждается, что остаток стека неизбежно получает applied или что реальные данные мира уже повреждены.
