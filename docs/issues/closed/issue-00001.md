## Общее описание проблемы

В исходном срезе имя каталога checkout — TheWitcherTRPG-RB-Version, а id манифеста — TheWitcherTRPG. После исправления id равен TheWitcherTRPG-RB-Version; описание исходного отказа ниже сохранено как основание issue. В установленном Foundry 14.367.0 серверный fromManifestPath явно сравнивает id с basename каталога и возвращает null при несовпадении. Изолированное исполнение настоящего метода с текущим путём и реальным JSON воспроизвело этот отказ до конструктора System.

Это подтверждённая техническая граница выбранного метода. Сканирование пакетов работающей службой, её список систем, журналы и загрузка мира в этой проверке не выполнялись; фактическое состояние запущенного экземпляра не установлено.

## На что влияет в системе

До исправления при передаче текущего пути штатному fromManifestPath пакет не создавался; вызывающий getPackages включает в коллекцию только ненулевые результаты. Следовательно, в этом маршруте выполнение module/TheWitcherTRPG.js, init/ready и доступность объявленных компонентов не наступают.

Это вывод из прочитанного загрузчика и изолированного метода, а не наблюдение работающего сервера. Конфликт двух уже загруженных систем с одинаковым ID не воспроизводился и не требуется для этого отказа.

## Почему это проблема

Несовпадение нарушает явное предусловие серверного загрузчика Foundry 14.367.0. Причина уже не основана только на сравнении двух строк: конкретный метод возвращает null с ошибкой «Invalid system» для фактического имени каталога.

Проверка была проведена на уровне входа манифеста. Положительный контроль с согласованным именем каталога проходит только эту границу и не доказывает полную валидность пакета, его установку или работу ресурсов.

## Где конкретно локализована в коде

- [system.json](../../../system.json), строка 2: до исправления id=TheWitcherTRPG, после — TheWitcherTRPG-RB-Version.
- Каталог checkout: /var/lib/foundryvtt/Data/systems/TheWitcherTRPG-RB-Version.
- Локальное ядро /opt/foundryvtt/dist/packages/package.mjs: ServerPackageMixin, методы getPackages, fromManifestPath и loadLocalManifest. Минифицированный файл; fromManifestPath начинается с байтового смещения 4266, фрагмент до следующего static loadLocalManifest — 1563 символа. SHA-256 файла: e77779bc83a740e7e9fa0903d5c83d4f5e5a7ef9112e552d1de9bfd40ea259ec.
- /opt/foundryvtt/dist/packages/system.mjs: System наследует ServerPackageMixin; собственный обход, отменяющий эту проверку, не найден.

getPackages получает каталоги через storage.getDirectories, передаёт manifestPath в fromManifestPath и добавляет только ненулевой результат. Реальный loadLocalManifest читает JSON и сохраняет путь; изолированный фасад воспроизводил именно эти входные данные.

## Предложение по изменению

**Принято и реализовано: самостоятельный пакет форка с ID `TheWitcherTRPG-RB-Version`, совпадающим с существующим каталогом. Ниже сохранены границы согласованного плана; фактические результаты и остаток проверки приведены в конце карточки.**

Цель — согласовать идентичность пакета и его технические обращения, сохранив текущие игровые формулы, типы документов, модели, имена классов и публичные действия. Закрытие issue требует отдельного подтверждения пользователя после проверки результата.

### Согласованное требование к совместимости

2026-09-16 пользователь уточнил: **обратная совместимость не требуется; совместимость со старыми миграциями также не поддерживается**. Это согласованное ограничение плана. Следующим поручением пользователь разрешил реализацию плана с отдельным ID форка.

Не добавлять aliases старого ID, двойную регистрацию namespaces, fallback-чтение прежних settings/flags или преобразование старых UUID ради совместимости. Старые миры, макросы и прежние форматы документов не являются целевыми входными данными исправления. Устаревшие миграции не требуется адаптировать под новый ID или сохранять ради старых данных. При этом штатная обработка актуальной схемы Foundry должна продолжать работать.

### Почему выбран этот вариант

В `/var/lib/foundryvtt/Data/systems` существует отдельный каталог `TheWitcherTRPG` наряду с текущим форком. Поэтому переименование форка в `TheWitcherTRPG` потребовало бы отдельно решить судьбу оригинального каталога и сохранило бы общую идентичность двух вариантов. Такое перемещение не предлагается как часть исправления.

Технически допустим и вариант установки форка вместо оригинала под ID `TheWitcherTRPG`. Он подходит для замены одной системы другой, но не обеспечивает двух независимо идентифицируемых пакетов. Выбор самостоятельного ID позволяет сохранить текущий каталог и оригинал рядом. Наличие каталогов не означает, что обе системы успешно загружены сервером.

`TheWitcherTRPG-RB-Version` допускается прочитанным `BasePackage.validateId` Foundry 14.367.0: латинские буквы, цифры, дефисы и подчёркивания; имя не относится к запрещённым системным именам. Это проверка отдельного ограничения, не доказательство валидности всего манифеста или работы мира.

| Значение | Принятое состояние |
| --- | --- |

| Scope системных flags | `TheWitcherTRPG-RB-Version` у производителей, прямых читателей, getFlag/setFlag |
| Пространство настроек | Согласованно заменено у register/get/set на ID форка; названия настроек сохранены |
| Пространство query | Согласованно заменены регистрация и отправители; имена методов и payload сохранены |
| Ключ компедиума травм | `TheWitcherTRPG-RB-Version.criticalWounds`, оба значения `initial` и `default` |
| UUID внутренних документов семи компедиумов | `Compendium.TheWitcherTRPG-RB-Version.<pack>.<type>.<id>`; имена packs, типы и ID документов сохранить |

ID пакета, путь ресурса, scope настройки, scope флага и имя query — разные контракты. Их нельзя менять одной безусловной заменой текста во всём репозитории.

Для flags изменение необходимо: `Document.getFlag/setFlag` проверяют разрешённые scopes, а `ClientDatabaseBackend.getFlagScopes` включает `core`, `world`, активный `game.system.id` и активные модули. Установленный рядом оригинал сам по себе не добавляет свой ID в этот список. В прямом JS-доступе имя с дефисами требует `flags['TheWitcherTRPG-RB-Version']`, а в литерале объекта — кавычек или вычисляемого ключа. Выражение `flags.TheWitcherTRPG-RB-Version` недопустимо как замена прежнего свойства.

Для settings прочитанный register формирует ключ из переданного namespace; требования равенства ID пакета в этом методе нет. Для query система сама регистрирует строковые имена. Их согласование с новым ID предлагается ради единой идентичности форка, а не выдаётся за причину исходного отказа загрузчика. Отправителей и получателей необходимо менять вместе.

В этом исправлении сохранена существующая организация кода. Новый слой конфигурации, переименование JS-классов и перестройка механизмов событий для устранения несовпадения ID не требуются.

### Миры и сохранённые данные

План ориентирован на новый мир форка и актуальные данные его компедиумов. Перенос существующих миров, settings, flags, старых UUID и пользовательских Macro не требуется и не входит в критерии приёмки. Старые миграции не должны становиться основанием для сохранения прежнего ID или создания совместимого слоя.

Существующий мир с `world.json.system = TheWitcherTRPG` продолжит ссылаться на оригинал; изменение system.json само по себе не переключает мир. Отказ от обратной совместимости не является поручением удалять или изменять существующие миры и БД.

### Критерии проверки исправления

1. На уровне загрузчика: ID равен basename, допускается validateId; настоящий пакет проходит полную валидацию, а не только прежний фасад конструктора. В списке систем работающего Foundry форк различим от оригинала; прежнее Invalid system предупреждение для него отсутствует.
2. На уровне ресурсов: все изменённые локальные адреса существуют; HTTP и браузер подтверждают ресурсы именно форка. Открываются Character/Monster/Loot, основные Item/configuration/ActiveEffect листы и используемые partials; нет ошибок загрузки по старому корню.
3. Settings/flags: настройка регистрируется и читается под согласованным scope; запись/чтение ChatMessage и Region flags проходят допустимый scope. Проверять сам контракт, не требовать успешности всех уже известных проблем словесного боя/регионов.
4. Query/socket: обе стороны используют одинаковые имена, доставка проверена для GM и обычного пользователя на выбранной доступной операции. Проблемы существующих whitelist/await/вложенных методов остаются отдельно; успешная регистрация имени не считается успешным выполнением любой операции.
5. Компедиумы: доступны семь заявленных пакетов, настройка травм указывает на fork collection; выборочные и автоматические проверки внутренних UUID разрешают документы форка. Проверить UUID поставляемых экспортов и тип Item/RollTable, сохраняя ID документов внутри текущего комплекта. Разрешение прежних UUID и импорт устаревших форматов не являются критериями приёмки.
6. Совместимость: нет добавленных aliases, двойной регистрации или fallback к старому namespace; удалённая legacy-ветка не участвует в подготовке актуальных документов. Проверять текущую схему, без регрессии старых миграций.
7. Справочник: существующие сущности/связи переадресованы без потери ID; существенные исправленные маршруты проверены, ссылки/хеши актуальны. Тесты справочника и проверки игры перечисляются раздельно.

Отсутствующий criticalWounds pack способен прервать ready в уже зарегистрированной [issue-00002](../potential/issue-00002.md). Сборка полного комплекта позволяет проверить issue-00001 на заявленной поставке; изменение поведения ready при отсутствии пакета относится к issue-00002 и не включается скрыто. Аналогично этот план не исправляет query/Region/бой попутно.
