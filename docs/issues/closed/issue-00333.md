### Наблюдение Б13: одна вещь в двух контейнерах

Исходное состояние: одна свободная вещь и два пустых контейнера у Actor, оба пользователя имеют OWNER. На двух настоящих листах выполнены drag в разные контейнеры. Временная обёртка только тестовых updateDocuments задержала отправку, пока оба клиента не подготовили свои изменения, затем отпустила оба штатных запроса. Хранение/ответы Foundry не подменялись; обёртка снята в finally.

Оба клиента увидели один UUID `Actor.HA3MdxadK3TxHSEW.Item.NjRIjNETQmaldpsF` в двух content-массивах, isStored=true. Перезагрузка QA-Player подтвердила сохранённое двойное членство. Это воспроизводимый конфликт, **не свидетельство частоты при обычных ручных действиях**. Причина в текущей реализации: `busyOwners` действует только внутри одного JS-клиента; `relocate`/`locationPatches` не сериализуют записи разных клиентов. Локальная проверка сохранения каждой пачки не обнаруживает появление второго родителя. Связано с [issue-00157](issue-00157.md); пользователь принял [ограничение одновременных переносов](../../documentation/known-limitations.md#container-concurrency), исправление не требуется.

Доказательства: `20-race.mjs`, `race-observed.json`, результат `21b-guards.mjs`, снимок диагностики. Данные конфликта сохранены в артефактах до удаления fixtures.

### Наблюдение Б15: native update холодного компедиума

В QA-Player появилось `TypeError: Cannot read properties of undefined (reading '_source')` в `ClientDatabaseBackend.#handleUpdateDocuments`, доставленный bundle `foundry.mjs:81144`. Это наблюдение об установленной Foundry 14.367. ### Точный контракт контейнера

- Экземпляры у Actor и в Items: `system.content` содержит UUID документов **той же коллекции**. Содержимое скрывается через `isStored`; вложенный вес считается обходом полного дерева по актуальным scalar quantity/weight, без повторного прибавления prepared storedWeight дочернего контейнера.
- Самодостаточный шаблон pack: nullable `system.templateContent = {version:1, sourceUuid, items:[{sourceUuid,data,items}]}`. Живые content-ссылки внутри payload отсутствуют. sourceUuid служит картой переназначения внутренних ActiveEffect.origin и не разрешается как действующий источник. Произвольные ссылки в описаниях/flags не переписываются.
- `WitcherItems` отключает keepId до штатной ветки замены мирового Item. `WitcherItem.createDocuments` разворачивает шаблон в одну native пачку и возвращает запрошенные корни; toCompendium собирает дерево. Существующая штатная команда Duplicate через clone(save:true) тоже создаёт независимое дерево; новая кнопка копирования не добавлена.
- `storeItem/importToActor/extractItem` ожидают сохранение и проверяют результат. В одном клиенте параллельная операция по владельцу блокируется; снимки и компенсация ограничивают последствия отказа. **Это не серверная транзакция и не доказательство отсутствия гонок двух клиентов.** При неполном восстановлении выдаётся ошибка и сохраняется последняя доступная копия.
- Удаление наполненного дерева вызывает одно явное подтверждение; безопасная кнопка по умолчанию — отмена. Отмена/закрытие не меняет данные; подтверждение удаляет дерево и внешнее членство. Внутренний перенос не спрашивает второй раз. Удаление всего Actor остаётся штатным удалением Actor.
- Повреждённая ссылка отображается отдельно; явная очистка убирает только ссылку. Нет автоматического обращения к чужому Item. При повреждённом дереве операции, требующие его полной сохранности, отказывают.

| Действие | Результат |
| --- | --- |
| Из каталога предметов мира или компедиума в контейнер | Создаётся самостоятельная копия с новым UUID. Источник сохраняется |
| Из инвентаря персонажа в его контейнер | Существующий предмет помещается внутрь, без копирования |
| Из одного контейнера в другой | Предмет полностью перемещается: исчезает из первого и появляется во втором |
| Извлечение из контейнера | Предмет возвращается в инвентарь владельца |

Каталог предметов мира и инвентарь персонажа различаются: первый служит источником копии, второй содержит уже существующие экземпляры. При перемещении между контейнерами одного персонажа сохраняется существующий экземпляр; при смене персонажа-владельца технический UUID может измениться, но операция остаётся перемещением с удалением экземпляра у отправителя. Контейнер получателя не должен оставаться связан с предметом из инвентаря отправителя. Порядок записей и обработка отказов определяются в техническом плане.

«Владелец» здесь означает персонажа, в чьём инвентаре находится контейнер. Учёт игровой собственности, воровство и отдельная ссылка на персонажа-собственника в эту работу не входят; права пользователей Foundry сохраняют своё отдельное назначение. Новую кнопку намеренного копирования сейчас не добавляем.

**Уточнение пользователя при проектировании .00033:** мировой каталог и компедиумы содержат шаблоны, в том числе наполненные. ### П01. Безопасное извлечение — 00313/00314/00315

Основной файл — [utils/extract.mjs](../../../utils/extract.mjs). Сейчас он сначала удаляет корневые JSON, требует существующий выходной каталог и не очищает старые вложенные файлы.

Предлагаемый алгоритм **для одного pack**:

1. Проверить входной каталог, список pack и возможность подготовки результата. Не считать любой посторонний файл базой. Выходную родительскую папку создавать при необходимости.
2. Извлекать pack целиком в отдельный уникальный временный каталог на том же файловом разделе. Он должен находиться **вне `packsJson`**, поскольку `utils/packs.mjs` перебирает его дочерние каталоги. Существующий экспорт пока не трогать.
3. Сохранить `folders:true`, `omitVolatile:true` и исключение `createdTime`, `modifiedTime`, `lastModifiedBy`. Дождаться завершения CLI, проверить читаемость JSON и состав экспорта по документам исходной тестовой базы. Пустая библиотека допустима; отсутствие файлов само по себе не доказывает отказ.
4. После успешного извлечения переименовать прежний каталог pack в отдельную резервную папку; поставить подготовленный каталог на прежний путь. Таким образом новый набор целиком заменяет старый, включая удалённые/перемещённые вложенные документы.
5. Если установка нового каталога не завершилась, восстановить прежний. Если восстановление тоже не удалось — не удалять оставшиеся данные и вывести точные пути и ошибку. Не продолжать работу как при успешной замене.
6. Удалять резервную копию только после подтверждения результата; диагностически сообщать, какие pack завершены. При ошибке следующего pack ранее успешно обработанные pack остаются обработанными. Это не общая транзакция всех библиотек и не атомарность двух переименований при аварии процесса.

В журнале различать извлечение, установку результата и очистку. Повторный запуск не должен удалять неизвестную оставшуюся резервную папку. Проверять совпадение файлового раздела для rename; не подменять его разрушительным copy/delete при EXDEV.

Метаданные доступа действующих каталогов — отдельная граница. Скрипт не назначает права/владельца и не заменяет каталог ради обхода ограничений; если подготовленный результат получит неподходящие метаданные, остановиться до установки и сообщить пользователю. Первое тестирование — только на изолированных базах/каталогах, без изменения прав. Проверку доступности новых файлов службе после реального обслуживания выполняют отдельно, когда пользователь назначит права.

`utils/packs.mjs` и `package.json` — потребители и точки запуска; менять их только если реально потребуется согласованный параметр рабочего каталога для изолированного запуска. Для тестов предпочтителен запуск существующего CLI из временного cwd. Не изменять содержимое семи действующих библиотек ради теста.

### П06. Контейнеры, экземпляры и наполненные шаблоны — 00156/00161

#### П06.1. Принятые требования и предлагаемые инварианты

Дополнение пользователя 2026-09-17: контейнеры каталога мира/компедиума — **шаблоны, которые могут быть наполненными**; содержимое такого контейнера тоже является шаблонами. При импорте в мир всему дереву создаются новые UUID. Пустой шаблон — частный случай. Требование также учитывается при последующем создании экземпляров у Actor.

Предлагаемые инварианты реализации:

- У реального предмета Actor не более одного непосредственного контейнера; дочерние предметы физически остаются embedded Item того же Actor. Вложенность выражается ссылками и не превращает Item в родителя embedded Item.
- Размещение/извлечение в пределах Actor сохраняет UUID, quantity, эффекты и пользовательские поля. Меняются только принадлежность контейнеру и необходимый `isStored`; перемещение между Actor создаёт новые документы у получателя и удаляет экземпляры у отправителя после проверки результата.
- Импорт шаблона копирует всё дерево, включая вложенные контейнеры и эффекты; каждый повторный импорт независим. Количество сохраняется целиком, дробление стопок и автоматическое слияние по имени не выполняются.
- Ссылки **содержимого** переписываются на новые UUID внутри полученного дерева. Ссылки на рецепты, заклинания и другие внешние справочные документы не переписываются массовой заменой строк UUID. Внутренние ссылки эффектов/служебные origin обрабатываются адресно по карте копирования, внешние не присваиваются чужому объекту.
- До записи проверяются разрешения, существование всего переносимого дерева, допустимые типы, единственное членство, самоссылки и циклы. Права Foundry не подменяются игровой собственностью. Чужой Actor не меняется лишь потому, что получатель доступен на запись.
- Содержимое контейнера учитывается в весе один раз, на любой вложенности, независимо от порядка подготовки Item. Полный вес дерева отличается от прямого вклада Item в Actor, который подавляется `isStored`. Не вызывать для вложенного содержимого calcWeight, возвращающий ноль для stored.

Для quantity контейнера предлагается сохранить существующий смысл: количество умножает собственный вес оболочки, а единственный список content учитывается один раз. Он не размножает содержимое автоматически. Проверка: предмет 2×3, внутренний контейнер весом 2 и внешний весом 1 дают общий вес 9 до и после перекладки; перенос к другому Actor сохраняет суммарный вес между отправителем и получателем. Автоматическое ограничение quantity контейнера до 1 не вводится этим планом.

#### П06.2. Согласованный самодостаточный шаблон и предлагаемый формат хранения

Текущее `system.content: UUID[]` подходит для связи реальных Item, но недостаточно для **самодостаточного** шаблона в компедиуме: обычный экспорт сохранит ссылки на чужие документы. В .00034 пользователь согласовал самодостаточное содержимое шаблона. Для реализации предлагается отделить переносимое описание от экземпляров, не вводя новый тип Item.

| Контекст | Предлагаемое представление |
| --- | --- |
| Экземпляр у Actor; наполненный шаблон в каталоге мира | `content` с UUID реальных Item того же Actor либо каталога мира; у мирового шаблона каждый дочерний Item тоже самостоятельный шаблон |
| Переносимый наполненный шаблон в компедиуме | Новое поле контейнера `system.templateContent` с деревом сериализованных данных Item; внешние UUID содержимого не сохраняются как рабочие ссылки |
| Создание из переносимого шаблона в мире/Actor | Развернуть дерево в реальные документы, выделить новые ID/UUID, записать новую карту content; очистить templateContent у созданных контейнеров, чтобы не держать второй изменяемый источник истины |

`templateContent` — **предлагаемое имя/формат**, не существующее поле. Самодостаточное хранение данных дерева уже принято пользователем в .00034; конкретная схема и имя поля ещё являются деталями реализации. Записи внутри него являются описаниями будущих Item, а не якобы существующими embedded-документами с Foundry UUID. После импорта реальными документами становятся и контейнер, и все его потомки. Такой формат позволяет экспортировать один наполненный контейнер без обязательной публикации его содержимого отдельными строками компедиума.

Нужны явная схема/валидация сериализованных записей, сохранение значимых данных и эффектов, проверка типов и дерева. Не выполнять код из данных шаблона. Сериализация не переносит чужие права доступа; использовать штатную очистку служебных полей Foundry. Не добавлять привилегии создаваемым документам. В режиме компедиума лист должен уметь **показать** дерево шаблонов без fromUuid для его внутренних записей. Пользователь в .00034 согласовал наполнение/редактирование в каталоге мира Items → штатный экспорт в доступный для записи pack. Редактор всех вложенных шаблонов внутри самого компедиума не разрабатывается. Для изменения уже опубликованного шаблона его импортируют в Items, правят и снова экспортируют; во время повторного экспорта явно используют штатный выбор создания/замены записи pack.

Каталог мира также служит конструктором шаблона: добавление каталожного Item создаёт отдельный мировой Item и ссылку на эту копию. Перемещение между двумя мировыми контейнерами меняет принадлежность существующего дочернего шаблона; извлечение оставляет его самостоятельным Item каталога. Перетаскивание экземпляра Actor в мировой контейнер-шаблон в .00034 **согласовано как копирование**: создать новые мировые документы всего копируемого дерева; у Actor сохранить исходные вещи, ссылки, количество и эффекты. Назначение в шаблон не является передачей игровой вещи. Прямой редактор содержимого pack не добавляется; штатный экспорт готового контейнера Actor в компедиум сериализует копию и сохраняет Actor. Физическое хранилище в игровом мире (например, сундук в замке) принадлежит отдельному Actor; перенос вещи туда использует правила перемещения между владельцами, а не копирования в Items.

#### П06.3. Точки внедрения и проверка контрактов Foundry

Предлагаются два небольших специализированных модуля: `module/item/containerOperations.js` для операций с экземплярами/проверок дерева; `module/item/containerTemplates.js` для сериализации и разворачивания шаблона. Имена — проектные. Не создавать общий движок миграций или универсальную транзакционную платформу.

1. **Лист контейнера:** делегировать операции сервису, ждать их завершения; добавить настоящий dragstart для строк. Сейчас общий лист регистрирует только drop, а строка содержимого не предоставляет полноценный drag-путь. UUID/источник строки передавать в стандартном Item drag payload с дополнительным контекстом контейнера; получатель проверяет членство по фактическим документам, не доверяет payload.
2. **Actor Drop:** для контейнеров импортировать дерево специализированным путём, минуя `Actor.addItem` со слиянием по имени. Проверку сортировки существующего предмета того же Actor выполнить до преобразования Document в plain object. Обычные предметы вне контейнерного сценария продолжают прежний путь; П07 меняет только подготовку экипировки оружия.
3. **WitcherItem.toCompendium:** сериализовать дерево доступного мирового/Actor-контейнера в переносимые данные. Метод синхронный: использовать уже доступные дочерние Item того же владельца; при нарушении дерева отказать, а не экспортировать неполную копию. Для уже переносимого pack-шаблона сохранять валидированное дерево. Не патчить ядро Foundry.
4. **WitcherItem.createDocuments:** узко обработать данные контейнеров с templateContent; для назначения в pack сохранить шаблон, для мира/Actor развернуть реальные документы. Сохранить контракты остальных типов, parent/pack, create options и порядок результата. Внутренняя рекурсия сервиса должна быть исключена явным внутренним контекстом. Возвращать вызывающему документы запрошенных корней, а не неожиданно все служебно созданные потомки; штатные события должны охватывать и созданное содержимое.
5. **Импорт в мировой каталог:** предложена специализированная коллекция `module/item/collections/WitcherItems.js`, зарегистрированная через `CONFIG.Item.collection` в `module/TheWitcherTRPG.js`. Узкое преобразование контейнерного импорта должно очищать ID корня **до** проверки существующего документа и предотвращать штатную замену ранее импортированного контейнера. Остальные Item делегировать super. Проверить отдельно одиночный импорт, повторный импорт и Import All: один override createDocuments не перехватывает путь замены через updateDocuments.
6. Прежде чем писать П06.3, подтвердить на небольших изолированных вызовах точный контракт этих overrides в установленном ядре, включая veto, частичное создание и keepId. Если штатный путь не даёт нужной точки расширения, предложить корректировку плана, а не выполнять post-create создание потомков без контроля результата.

Обычное клонирование целого Actor, Adventure import, произвольная запись system.content макросом и взаимодействие со сторонними модулями не объявляются автоматически покрытыми. Сервис не должен ломать их штатный базовый вызов, но добавление всех обходных путей — отдельный объём. Доступные UI-пути создания/импорта самого контейнера, перечисленные выше, входят в приёмку обязательно.

#### П06.4. Записи, ошибки и повторные действия

Для одного Actor (либо коллекции мировых Item) подготовить новые массивы, не меняя подготовленную модель через push/splice до успешной записи. По возможности отправлять связанные обновления одной пачкой, затем проверять фактические документы. Обработчик должен возвращать/ожидать Promise до конца операции; исчезновение окна или уведомление не означает завершения записи.

Для переноса между Actor:

1. Получить и проверить исходное дерево, контейнеры и права; сохранить снимок затрагиваемых данных. На время собственной операции исключить повторный запуск для тех же предметов в этом клиенте.
2. Подготовить все копии с заранее определёнными новыми ID и связями. Создать получателю целое дерево без слияния по именам; проверить возвращённые документы и сохранённые значения. Частичный результат/undefined после veto не считать успехом.
3. Только после проверки приёмника удалить исходные экземпляры и прежнее членство. Не оставлять у получателя UUID отправителя. Проверить результат удаления и окончательные флаги обеих сторон.
4. При отказе до удаления источника убрать только копии данной попытки и восстановить затронутые ссылки. Если уже произошло частичное удаление или компенсирующая запись тоже отказала, не удалять последнюю сохранившуюся копию. Выдать явную ошибку с перечнем источников/получателей и сохранить диагностику для восстановления.

Это компенсация нескольких операций, **не обещание атомарной транзакции Foundry**. Повторно проверить членство непосредственно перед сохранением; обнаруженный конфликт отменяет операцию. Локальная блокировка не защищает от второго клиента или обрыва процесса. Проверка параллельных действий двух клиентов обязательна для оценки предела; при воспроизводимой потере/тихом дублировании не объявлять перенос полностью принятым и отдельно согласовать координацию операций. Новый привилегированный GM socket без такого решения не добавлять.

При недоступном UUID подготовка листа показывает строку с исходным UUID/заглушкой и сообщает, что вес неполон, вместо падения или представления неизвестного веса как достоверного нуля. Разрешить явное удаление **повреждённой ссылки** без обновления отсутствующего/чужого документа; отделить эту команду от успешного извлечения вещи. Нажатие для UUID, не состоящего в контейнере, ничего не меняет. Неразрешённую часть дерева при импорте/переносе не терять молча — остановить операцию до записи.

Для [00162](issue-00162.md) в .00034 принято **удаление с подтверждением и всем содержимым**. Прежнее предложение запрета не применяется. План реализации:

1. При пользовательском удалении наполненного контейнера показать подтверждение, прямо сообщающее об удалении вложенных вещей. До ответа не выполнять записи. Отмена/закрытие окна сохраняет всё дерево; смысл подтверждённого удаления по умолчанию — потеря всех его вещей, а не возврат в инвентарь. Это не требование автоматически подтверждать действие или назначать опасную кнопку действием Enter.
2. До удаления собрать дерево и проверить принадлежность документов и разрешения. Операция затрагивает только этот контейнер и его содержимое; исходные шаблоны мира/компедиума, по которым создавались копии, и посторонние Item не удаляются. Повреждённая ссылка на чужой документ не даёт права каскадно удалять его.
3. Удалить вложенные вещи и контейнер, убрать членство корня во внешнем контейнере, если оно было, проверить сохранённый результат. В инвентаре не остаются скрытые осиротевшие Item. Для мирового шаблона удаляются его собственные дочерние копии; удаление переносимой записи pack удаляет сериализованное содержимое вместе с ней, а не исходные Item.
4. Общий сервис/контракт документа должен охватывать удаление через лист и каталог; подтверждение запрашивает инициирующий клиент один раз для всей операции. Служебное удаление отправителя при переносе использует уже подготовленный план переноса, не запускает повторное пользовательское удаление и не затрагивает копии получателя. Удаление всего Actor не должно порождать отдельные диалоги на каждый вложенный контейнер.
5. Отказ/частичное удаление обрабатывать как незавершённую операцию: сохранить снимок и фактический список оставшихся документов, сообщить об ошибке, не показывать успех. Проверить восстановление при доступных компенсирующих записях. Атомарность нескольких записей Foundry не обещается.

Перед реализацией уточнить документные точки вызова по установленному ядру: нельзя ограничиться кнопкой листа, а затем позволить другому штатному пути тихо оставить содержимое. Это техническая проверка принятого поведения, а не повторное согласование судьбы вещей.
