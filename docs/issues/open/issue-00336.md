## Общее описание проблемы

При первой установке критической травмы с вложенным активным эффектом Item и AE сохраняются, штраф применяется, но операция возвращает `failed/uncertainWrite`. Пользователь получает сообщение, что запись травмы не удалось подтвердить.

## На что влияет в системе

Результат операции получения травмы и уведомление пользователя. В воспроизведении травма ноги уже снижала Скорость 8 → 6. Ложное сообщение может побудить повторить успешно выполненное действие. Отсутствие записи в БД этим сообщением не подтверждается.

## Почему это проблема

Проверка результата считает предусмотренную инициализацию часов AE несовпадением стадии. Успех должен подтверждаться по ожидаемым сохраняемым данным; реальные отклонения записи при этом должны обнаруживаться.

## Где конкретно локализована в коде

- [criticalWoundOperations.js](../../../module/item/criticalWoundOperations.js): `writeStage` готовит часы ожидаемых AE через [initializeEffectStart](../../../module/activeEffect/effectApplication.js); `stageMatches` строго сравнивает поля AE, кроме `_stats`.
- [WitcherItem.createDocuments](../../../module/item/witcherItem.js) вызывает [assignedItemData](../../../module/activeEffect/effectFamilies.js). До .00144 обработчик повторно сбрасывал уже подготовленный start и сокращал duration. В .00144 внутреннее создание с WOUND_INTERNAL сохраняет эти часы; обычный импорт прежний. Вложенный AE._preCreate в этом пути не вызывается; первоначальная атрибуция ему была неточной.
- [damageMixin.applyCritWound](../../../module/actor/mixins/damageMixin.js) и ручная установка вызывают общий сервис; `reportWoundResult` сообщает ошибку по его результату.

## Предложение по изменению

[Проект .010](../../tasks/task-0012-temporary-hp.md#task-0012010): до первого create заполнить отсутствующие часы подготовленных AE тем же helper, отправлять и проверять одинаковые ожидаемые данные. Сохранить строгий stageMatches и реальные ошибки записи, однократность коррекции длительности и исходный шаблон. Дополнение .00144 сохраняет подготовленные часы в общем пути Item; нужны проверки настоящего `WitcherItem.createDocuments → assignedItemData` и игровое повторение. Замену существующей стадии не переписывать.

## Воспроизведение и доказательства

На .00139 вызов `applyCritWound` для leftLeg/simple при отсутствии соответствующей травмы дал failed при сохранённом Item/AE и работающем штрафе. Аналогичный прямой вызов installWound воспроизведён у monster. В сравнении запроса и результата из сравниваемых полей отличался `effects[0].start`: null → объект времени/боя. Добавленный ядром ownership уже исключён из сравнения.

[Протокол .008](../../analytics/task-0012-checks.md#browser-00139); серверные артефакты `work-cat/witcher-task0012-browser-20260920/wound-probe.json`, `wound-game.json`, `wound-ui.json` относительно Data. Повтор существующей травмы и проверенные переходы стадий работали. Это не принятая [гонка двух клиентов](../../documentation/known-limitations.md): ошибка возникла в одной последовательной операции. Проверка более старой версии в запущенном мире не выполнялась; её происхождение не приписывается без такого доказательства исключительно TASK-0012.

## Игровая проверка .00142 — отчёт .00143

Исходное ложное сообщение для обычной травмы устранено, но обнаружен остаток: assignedItemData повторно сбрасывает start и сокращает срок, уже подготовленный writeStage. Настроенный срок3 раунда превращается в1 вместо2; три из шести боевых сочетаний возвращают failed/uncertainWrite. Штатные AE со сроком1 этого числового расхождения не проявляют. Исправление всей цепочки и тест с настоящим WitcherItem.createDocuments ещё нужны. Карточка open; автоматическое закрытие исключено.

[Протокол](../../analytics/task-0012-checks.md#browser-00142), [состояние задачи](../../tasks/task-0012-temporary-hp.md#browser-00142). Игровой код в ходе приёмки не менялся.
