# Работа с проблемами

Проблемы хранятся в [docs/issues](../issues/README.md). Каждая проблема — отдельный Markdown-документ, составленный по [шаблону](../issues/templates/issue.md).

## Регистрация и согласование

1. Обнаружив возможную проблему, агент сообщает пользователю факты, предполагаемое влияние и предлагает зарегистрировать её.
2. После согласования регистрации агент создаёт карточку в `potential` и добавляет её в общий реестр.
3. Подтверждение пользователем наличия проблемы и необходимости исправления позволяет перевести карточку в `open`.
4. Конкретные изменения для исправления согласовываются отдельно до их выполнения. Наличие открытой проблемы не заменяет такого согласования.
5. После проверки результата агент описывает его пользователю и предлагает закрытие. Карточка перемещается в `closed` только после подтверждения пользователем.

**Согласие на регистрацию не означает подтверждения проблемы или разрешения на исправление.** Если поручение уже явно включает нужное согласование, повторно запрашивать его не требуется. Не выводить согласие на одно действие из согласия на другое.

Любые изменения карточек и новые решения подчиняются общему [порядку согласования](development.md). Найденная проблема не становится задачей автоматически; задачи формируются с пользователем в [отдельном разделе](../tasks/README.md).

## Каталоги и статусы

| Каталог | Назначение | Основание для размещения |
| --- | --- | --- |
| `potential` | Найденные, но ещё не подтверждённые пользователем проблемы | Согласована регистрация наблюдения |
| `open` | Открытые проблемы, которые необходимо исправить | Пользователь подтвердил проблему и необходимость исправления |
| `closed` | Закрытые проблемы, закрытие которых подтверждено пользователем | Пользователь подтвердил закрытие и его основание |

Воспроизведение проблемы агентом — доказательство для обсуждения, но не подтверждение пользователя. До такого подтверждения карточка остаётся в `potential`.

Если исправление выполнено, но закрытие ещё не подтверждено, карточка остаётся в `open`; результат и проверки записываются в ней. Неподтверждённую проблему можно закрыть из `potential`, например если наблюдение не является ошибкой или дублирует другую карточку. Для этого также нужны решение пользователя и записанная причина закрытия.

Статус определяется каталогом, в котором находится карточка. README каждого каталога объясняет его назначение и сохраняет каталог в Git, даже когда карточек нет.

## Идентификаторы и перемещение

- Имя файла — `issue-00001.md`: префикс `issue-`, пять цифр и расширение `.md`. ID этой карточки — `issue-00001`.
- Нумерация сквозная для всех трёх статусов. Перед созданием проверить карточки во всех каталогах и общий реестр; следующий номер — на единицу больше наибольшего выданного. При пустом реестре начать с `issue-00001`.
- ID не переиспользуются. У одной проблемы одна карточка; при смене статуса перемещать её, сохраняя ID и имя файла, а не создавать копию.
- Вместе с перемещением обновлять статус и путь в реестре, а также все ссылки на карточку в документации.
- Заголовок внутри документа содержит ID и понятное описание проблемы. README и файл шаблона не участвуют в нумерации.

## Содержание карточки

Пять обязательных разделов:

1. Общее описание проблемы.
2. На что влияет в системе.
3. Почему это проблема.
4. Где конкретно локализована в коде.
5. Предложение по изменению.

Также указывать дату, ветку и коммит, версию Foundry, шаги воспроизведения, ожидаемый и фактический результаты, доказательства и решения пользователя. Для закрытия записывать основание, выполненные проверки и подтверждение пользователя.

Отделять проверенные факты от предположений. Если воспроизведение, точная причина, место в коде или решение ещё не установлены, прямо указывать это. Не заполнять пробелы догадками. Для локализации давать относительные ссылки на файлы и названия полей, функций или обработчиков; номера строк относятся к указанной версии кода.

Предложение по изменению остаётся предложением до согласования. При недостатке данных описывать необходимую проверку и условия выбора решения, а не выдавать предполагаемое исправление за принятое.

Аналитика может обосновывать выводы, а задача — описывать согласованную реализацию; они ссылаются на карточку, не подменяя её. Связь с задачей добавляется, только когда задача создана после согласования.
