# Проверки

Состав проверок определяется согласованной работой. Результат должен показывать, что действительно выполнено, на какой версии и какие свойства этим подтверждены.

## Текущие инструменты

В [package.json](../../package.json) есть команды сборки и извлечения компедиумов; команда `npm test` не определена. Создание тестового стенда не считается поставленной задачей.

## Принципы

- Проверять наблюдаемый результат, а не совпадение теста с внутренними шагами реализации.
- Для модели или обработчика использовать настоящий код, если проверяется именно его поведение.
- Ожидаемый результат не вычислять той же функцией, которую проверяет тест.
- Явно обозначать подмену окна, записи в БД или других зависимостей.
- Различать локальную проверку, браузерный сценарий, сохранение документов и работу нескольких клиентов.
- Не выдавать запланированную проверку за выполненную.

Для документации достаточно проверить содержание, ссылки, структуру Markdown и состав изменений. Игровые тесты не требуются только из-за изменения Markdown.

Команды сборки и извлечения packs записывают данные. Их запуск согласовывается как действие с записью, а не используется как обычное чтение.

## Объём проверок справочника

**По умолчанию проверять справочник по области изменений. Полный прогон не является обязательным шагом каждого изменения системы.** Это правило согласовано пользователем 2026-09-16 для ограничения затрат на обслуживание справочника.

При обновлении записей справочника вслед за изменениями исходников:

1. Проверить целостность графа, ссылки и актуальность хешей одним запуском `python3 -B docs/analytics/system-index/query.py check --freshness --format json` из корня репозитория.
2. Сверить изменённые записи с исходниками: значения, адреса строк, владельцев, зависимости и границы процессов. Обновление хеша само по себе не подтверждает правильность описания.
3. Запустить существующие тесты и CLI-сценарии затронутых разделов и непосредственно зависимых связей. Техническое переименование ID, путей или namespaces само по себе не требует запуска всех сценариев справочника.
4. После исправления найденного несоответствия повторить соответствующую проверку и зависимые от неё проверки. Расширять охват при новых ошибках или признаках более широкого влияния; успешно завершённые несвязанные проверки без причины не повторять.

Полный набор тестов справочника запускать при изменении его механизма поиска/обхода/валидации, формата данных или общего контракта CLI, а также при подготовке контрольного выпуска либо по прямому поручению пользователя. В отчёте указывать основание полного прогона и фактический охват проверок. Локальная ошибка в данных или ожидаемом значении теста не является автоматическим основанием для полного прогона.

Для правок только правил, навигации или поясняющего текста достаточно проверки затронутых документов и ссылок. Если такие документы входят в контролируемые ссылки справочника, обновить зависимые хеши и проверить актуальность; игровые тесты и полный набор CLI-сценариев из-за этого не запускать.

Проверки самого игрового кода выбирать отдельно по изменённому поведению. Сокращение регрессии справочника не отменяет необходимых проверок системы Foundry.

## Отчёт

Записывать команду или сценарий, фактический результат и ограничения. Успешное локальное чтение не подтверждает HTTP-доступ службы Foundry; применимые правила доступа находятся в [file-access.md](file-access.md).
