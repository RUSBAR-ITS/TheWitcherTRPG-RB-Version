### Решение 01 — Настраиваемые параметры выдачи временных ПЗ

**Принято пользователем 2026-09-19; оформление 14.3.1.00121.** Пользователь поручил сделать настраиваемым каждый из обсуждённых параметров способности. Настройки принадлежат конкретной способности профессии; механизм не должен определять её поведение по названию «Рвение» или навязывать всем способностям числа этого правила.

| Параметр | Требование | Пример «Рвения» по русским книгам |
| --- | --- | --- |
| Параметр получателя для сложности | Выбирается в настройках способности | Действующий Интеллект получателя |
| Множитель сложности | Задаётся в настройках | 3 |
| Предел учитываемого превышения сложности | Задаётся в настройках | 5 пунктов |
| Количество / формула временных ПЗ | Настраиваемые формула и режим Fix / за каждый пункт превышения, см. [решение 03](#decision-03); округление вверх или вниз по [решению 11](#decision-11) | 1d6 за каждый учитываемый пункт превышения, максимум 5d6 |
| Длительность | Значение/формула и единица; автоматически только раунды в бою, остальные сроки текстовые, см. [решение 05](#decision-05) | Уровень Рвения × 2 раунда |

Основания: [основная книга, с. 65](../../../TheWitcherTRPG-RB-Version-archive-2026-09-10/assets/books/core_rulebook.md#page-065) и [русский «Фолиант Хаоса», раздел «Рвение»](../../../TheWitcherTRPG-RB-Version-archive-2026-09-10/assets/books/tome_of_chaos.md#рвение-эмп). При сложности 15 и результате проверки 18 выдаётся сумма трёх отдельных d6; при превышении 8 учитываются только 5 пунктов. Максимум 5 относится к числу учитываемых пунктов, а не к итоговым ПЗ. Ограничение «на одну цель раз в день» также указано в книгах; по [решению 02](#decision-02) его контролирует мастер.

Примеры произвольного ввода 5 и 5+2 из обсуждения относятся к возможностям настройки, а не к правилу Рвения. Смысл поля количества уточнён пользователем в [решении 03](#decision-03): поддерживаются оба режима, Fix и за каждый учитываемый пункт превышения.

**Проверка текущего устройства, dev, HEAD `bc84c57504850d07506d8a486c0a628806417ab5`:** [professionSkillData](../../module/data/item/templates/professionSkillData.js) задаёт отдельные имя, параметр, уровень и skillUsage; [TemporaryHealth](../../module/data/item/templates/profession/temporaryHealthData.js) уже содержит все пять полей с начальными значениями int / 3 / 5 / d6 / 2*@level. Они выведены в [редакторе способности](../../templates/sheets/item/configuration/partials/profession/skillPathSkillPart.hbs). [doProfessionSkillUsage](../../module/actor/mixins/professionMixin.js) читает эти настройки, но сохраняет описанные в issues ошибки формул/данных. В этом обработчике нет проверки суточного ограничения. Существующие подходящие поля следует использовать при проектировании; повторная параллельная система настроек этим решением не требуется.

**Состояние:** решение записано; код, поля, значения по умолчанию, игровые данные и статусы issues не менялись. Режимы количества определены в [решении 03](#decision-03). Необходимость проверки в Fix определяется [решением 04](#decision-04). Ещё нужно согласовать оставшиеся детали формул и устойчивую идентичность записи. Выбор применяющего или получателя как источника значения определён в [решении 15](#decision-15). Выбор базового или действующего значения навыка/характеристики определён в [решении 14](#decision-14). <a id="decision-03"></a>
### Решение 03 — Формула количества и расширяемые режимы Fix / за каждый пункт

**Принято пользователем 2026-09-19; оформление 14.3.1.00123.** Пользователь одобрил формулу количества за каждый учитываемый пункт превышения и дополнил её режимом Fix. Конфигурация должна допускать последующее добавление режимов и использование расчёта другими механиками.

| Режим | Смысл количества | Примеры |
| --- | --- | --- |
| Fix — за применение | Полная заданная формула вычисляется один раз; количество не умножается на превышение сложности | 5 → 5 ПЗ; 5+2 → 7 ПЗ; 1d6+2 → один бросок d6 + 2 |
| За каждый пункт превышения | Полная формула вычисляется отдельно для каждого учитываемого пункта; результаты складываются. Сначала действует настраиваемый предел превышения | При трёх учитываемых пунктах: 1d6 → сумма трёх d6; 5 → 15 ПЗ; 1d6+2 → 3d6 + 6; 5+2 → 21 ПЗ |

Кости разных пунктов независимы: при трёх пунктах результат одного d6 не умножается на три. Округление по [решению 11](#decision-11) применяется один раз к итоговой сумме, а не отдельно к каждому слагаемому. Для «Рвения» по русским книгам используется второй режим, формула 1d6 и предел 5. Его режим и числовые значения остаются настройками способности, не определяются её именем.

Режим хранится как отдельный выбор с возможностью добавить следующие значения; одной булевой галочки для двух режимов недостаточно для требуемого расширения. При проектировании выделить расчёт количества так, чтобы его можно было повторно использовать без зависимости от конкретной профессии. Состав будущих режимов и подключение других механик в эту порцию не добавляются автоматически; прежняя строковая склейка превышения и формулы должна уступить вычислению согласно выбранному режиму.

**Уточнение по решению 04:** в Fix необходимость проверки задаётся отдельной галочкой; для режима за пункт превышения проверка обязательна. Единицы и автоматизация длительности определены в [решении 05](#decision-05); для используемых навыков/характеристик предусмотрен выбор базового или действующего значения по [решению 14](#decision-14); принадлежность значений задаётся по [решению 15](#decision-15), интерфейс составления формул определён в [решении 16](#decision-16), точный синтаксис ссылок будет предложен в техническом проекте. Допустимость вычисленного числового результата контролируется автором настройки по [решению 13](#decision-13).

**Будущая приёмка этого решения:** два режима с одной и той же формулой; константа, арифметика и кости; независимые результаты по пунктам; ограничение числа пунктов до вычисления; книжный пример «Рвения». Это требования к проекту, не отчёт о выполненных тестах.

**Состояние:** решение записано; реализация, игровые данные и статусы шести issues не менялись.

<a id="decision-04"></a>
### Решение 04 — Галочка «Требуется проверка» для Fix

**Принято пользователем 2026-09-19; оформление 14.3.1.00124.** В режиме Fix необходимость проверки способности задаётся галочкой «Требуется проверка» в конфигурации способности.

- Галочка включена: сначала выполняется проверка способности против настроенной сложности. Временные ПЗ выдаются при успехе; формула количества Fix вычисляется один раз и не умножается на превышение сложности.
- Галочка выключена: выдача не требует проверки способности; настроенная формула количества Fix вычисляется один раз при применении.
- В режиме «За каждый пункт превышения» проверка остаётся обязательной: именно её результат определяет число учитываемых пунктов.

Галочка управляет проверкой способности, а не костями внутри формулы количества: Fix с формулой 1d6+2 без проверки по-прежнему бросает один d6 для определения выдаваемых ПЗ. Настройка суточного счётчика не добавляется — ограничение применений остаётся под контролем мастера по [решению 02](#decision-02).

**Будущая приёмка:** Fix с проверкой и без неё, успешная/неуспешная проверка, отсутствие зависимости количества Fix от превышения, сохранение бросков самой формулы при выключенной проверке; режим за пункт обязательно получает результат проверки. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; код, данные и статусы шести issues не менялись. Длительность уточнена в [решении 05](#decision-05); остальные вопросы проектирования ещё обсуждаются.

<a id="decision-05"></a>
### Решение 05 — Боевой отсчёт только для раундов, остальные сроки текстовые

**Принято пользователем 2026-09-19; оформление 14.3.1.00125.** В конфигурации длительности используются значение/формула и выбор единицы. Только раунды контролируются боёвкой; минуты, часы и дни служат текстовым описанием срока. Секунды исключаются из предлагаемого выбора.

| Единица | Поведение |
| --- | --- |
| Раунды | Отсчёт связан с боевой системой; течение мирового времени само по себе не должно расходовать эти раунды |
| Минуты, часы, дни | Отображается вычисленный срок для мастера; нет таймера и автоматического истечения по мировому или реальному времени. Завершение срока контролирует мастер вручную |

Значение/формула длительности вычисляется один раз при применении и сохраняется вместе с единицей; для «Рвения» это удвоенный уровень способности (в текущей конфигурации 2*@level). В проекте источник значения и выбор базы/действующего значения должны задаваться явно по [решению 14](#decision-14); один жёстко заданный смысл @level для всех способностей не утверждён. Текстовый срок вида «30 минут» не превращается в автоматический таймер ActiveEffect. Обновление страницы, перевод игрового времени и отдых сами по себе не должны истекать такой эффект или повторно бросать формулу его срока.

Текстовый способ учёта срока не отключает временные ПЗ: их выдача, отображение, поглощение урона и сохранение остатка продолжают работать. Это правило относится к проектируемой конфигурации TASK-0012; изменение таймеров всех остальных эффектов системы не согласовывалось.

**Зависимости, подтверждённые чтением текущего кода:** updateDerivedStat в [damageMixin](../../module/actor/mixins/damageMixin.js) перебирает this.temporaryEffects. В установленном Foundry14.367 getter Actor.temporaryEffects отбирает только active && isTemporary, а ActiveEffect.isTemporary зависит от duration.expiry или числового duration.value. Поэтому при проектировании расход нужно связывать с действующими записями временных ПЗ, а не с наличием таймера. В ядре ActiveEffect._prepareCombatBasedDuration при отсутствии подходящего боя/участника предусмотрен переход к отсчёту секунд; простого выбора native rounds недостаточно, чтобы заявить выполнение требования пользователя. Пути ядра: /opt/foundryvtt/client/documents/actor.mjs:163–168 и active-effect.mjs:225–226,417–451. Это чтение исходников, не игровой тест.

**Актуальное уточнение по решению 08:** единица «Раунды» сохраняется в данных эффекта и определяет способ учёта срока. До участия получателя в начавшемся бою отсчёт не идёт; затем включается раундовый контроль. По окончании этого боя эффект снимается, в том числе если получен до боя.

**Будущая приёмка:** секунды отсутствуют в выборе; формула/единица и текст сохраняются после reload; перевод мирового времени не уменьшает раунды и не истекает текстовые сроки; разрешённый боевой отсчёт работает; источник с текстовым сроком поглощает урон наравне с источником в раундах. Применение до боя и последующий запуск отсчёта проверяются по [решению 08](#decision-08). Это требования к проекту, не выполненные проверки.

**Состояние:** решение записано; код, данные, таймеры Foundry и статусы шести issues не менялись.

<a id="decision-07"></a>
### Решение 07 — Снятие раундового эффекта при завершении боя

**Принято пользователем 2026-09-19; оформление 14.3.1.00127.** По окончании боя раундовые эффекты временных ПЗ снимаются. В обсуждённом случае эффект создан в бою на 8 раундов, бой завершён после трёх: эффект снимается вместе с неиспользованными временными ПЗ, оставшиеся 5 раундов не сохраняются под ручным контролем и не переносятся в следующий бой.

Это согласованное поведение проекта TASK-0012. Обычные текущие и максимальные ПЗ при снятии не меняются. Сроки в минутах, часах и днях остаются текстовыми согласно [решению 05](#decision-05); общего изменения всех таймеров системы это решение не вводит.

**Уточнение принято в [решении 08](#decision-08):** эффект, полученный до боя с единицей «Раунды», при участии получателя в начавшемся бою переходит на раундовый отсчёт и также снимается по окончании этого боя. Отдельного постоянного ручного режима для него не остаётся.

**Будущая приёмка:** выдать временные ПЗ участнику боя с раундовым сроком, потратить часть урона и завершить бой до истечения срока — эффект и остаток временных ПЗ сняты; обычные ПЗ сохранены; после обновления страницы и начала следующего боя эффект не возвращается. Отдельно проверить обычное истечение заданных раундов до конца боя. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись.

<a id="decision-08"></a>
### Решение 08 — Единый контроль раундовых эффектов при вступлении в бой

**Принято пользователем 2026-09-19; оформление 14.3.1.00128.** Раундовый эффект определяется по выбранной единице длительности «Раунды», сохраняемой вместе с вычисленным сроком в данных созданного эффекта. Определять его по названию, тексту описания или наличию уже запущенного таймера не требуется.

- При применении вне боя временные ПЗ выдаются сразу, срок в раундах сохраняется; до участия получателя в начавшемся бою раунды не расходуются.
- При начале боя с получателем среди участников либо при вступлении получателя в уже начавшийся бой эффект переходит на раундовый контроль. Используется сохранённая длительность: формула повторно не вычисляется, временные ПЗ повторно не выдаются, потраченная часть не восстанавливается.
- В бою эффект снимается при истечении раундового срока. Если бой заканчивается раньше, эффект также снимается вместе с оставшимися временными ПЗ согласно [решению 07](#decision-07), независимо от применения до боя или во время него.
- Минуты, часы и дни сохраняют текстовый срок под контролем мастера по [решению 05](#decision-05).

Это заменяет [решение 06](#decision-06): отдельный вариант постоянного ручного контроля раундового эффекта исключён. Граница снятия при завершении боя для применения до боя согласована; вопрос больше не открыт. Правило относится к проектируемым эффектам временных ПЗ TASK-0012 и само по себе не расширяет работу на таймеры всех эффектов системы.

**Будущая приёмка:** сохранить единицу «Раунды» и вычисленный срок при применении вне боя; расходовать часть ПЗ и перевести мировое время — срок не уменьшается; начать бой с получателем либо добавить его в начавшийся бой — включается отсчёт сохранённого срока без повторной выдачи ПЗ. Обновление страницы не сбрасывает работающий отсчёт и остаток. Истечение раундов или завершение боя снимает эффект и остаток; обычные ПЗ не меняются. Для минут/часов/дней перехода на раундовый контроль нет. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные, таймеры Foundry и статусы шести issues не менялись.

<a id="decision-09"></a>
### Решение 09 — Расход временных ПЗ в порядке получения

**Принято пользователем 2026-09-19; оформление 14.3.1.00129.** При нескольких действующих источниках временных ПЗ сначала расходуется запас, полученный раньше. После его исчерпания остаточный урон переходит к следующему источнику; обычные ПЗ уменьшаются только на урон, не поглощённый всеми доступными запасами.

Пример: сначала получены 10 временных ПЗ от источника А, затем 20 от источника Б. При уроне 12 запас А исчерпан, его эффект снимается по [решению 10](#decision-10), Б = 18; обычные ПЗ не меняются. При уроне 35 оба запаса исчерпаны и их эффекты снимаются, обычные ПЗ уменьшаются на 5. Если ранний источник ещё имеет запас, поздний не расходуется.

Длительность и единица срока не задают приоритет расхода. Сортировка по ближайшему истечению и выбор источника отдельным диалогом не вводятся. При проектировании обеспечить сохранение порядка получения после обновления страницы и записи нового остатка; изменение порядка отображения эффектов не должно менять порядок расхода. Способ хранения устойчивого порядка определяется в техническом проекте вместе с идентичностью источника.

Текущий [updateDerivedStat](../../module/actor/mixins/damageMixin.js) перебирает найденные эффекты без отдельной сортировки по времени получения или сроку. Поэтому текущий порядок коллекции сам по себе не подтверждает выполнение нового контракта. Это согласованный порядок проекта, не утверждение о наличии такого общего правила в книгах. Правила суммирования и повторного применения данным решением не меняются; снятие самого эффекта после исчерпания запаса определено в [решении 10](#decision-10).

**Будущая приёмка:** два источника с разными моментами получения; урон меньше первого запаса, равный ему, превышающий его и превышающий оба запаса. Повторить после сохранения/обновления страницы; изменение остатка раннего источника не делает его новым. Разные сроки не меняют порядок; расход прекращается после полного поглощения урона, посторонние строки не расходуются как временные ПЗ. Исчерпанный эффект снимается по [решению 10](#decision-10). Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись.

<a id="decision-10"></a>
### Решение 10 — Снятие эффекта при исчерпании временных ПЗ

**Принято пользователем 2026-09-19; оформление 14.3.1.00130.** При полном расходовании запаса временных ПЗ эффект снимается сразу. Сохранять исчерпанный эффект с нулевым запасом до окончания срока или ручного снятия не нужно. Правило действует независимо от единицы длительности и наличия боевого отсчёта.

При частичном расходе эффект остаётся с уменьшенным запасом. При полном расходе снимается сам эффект, а остаточный урон продолжает поглощаться следующими действующими источниками в порядке [решения 09](#decision-09); после них остаток урона уменьшает обычные ПЗ. Само снятие не наносит дополнительный урон и не восстанавливает потраченные временные ПЗ.

**Следствие для составного эффекта:** снятие целого ActiveEffect завершает все его модификаторы. Это отличается от ошибки [issue-00023](../issues/potential/issue-00023.md), при которой посторонние строки ошибочно расходуются как временное здоровье. Пока запас не исчерпан, посторонние строки сохраняются без изменения; при исчерпании действует согласованное снятие эффекта. Бонусы, которые должны продолжаться независимо от этого запаса, при настройке следует оформлять отдельным эффектом. Автоматическое разделение составного эффекта этим решением не вводится.

**Будущая приёмка:** частичный расход оставляет эффект и сохраняет его другие строки; точное исчерпание снимает эффект без потери обычных ПЗ; превышение запаса снимает исчерпанный эффект и передаёт только остаточный урон дальше. Проверить раундовый и текстовый срок, несколько источников и сохранение результата после обновления страницы; завершившийся эффект не возвращается. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись.

<a id="decision-11"></a>
### Решение 11 — Настраиваемое округление количества временных ПЗ

**Принято пользователем 2026-09-19; оформление 14.3.1.00131.** В конфигурации выдачи временных ПЗ конкретной способности добавить выбор «Округление»: «Вверх» или «Вниз». Одно обязательное направление для всех способностей не задаётся.

| Выбор | Результат 2,5 | Результат 0,5 | Целый результат 3 |
| --- | --- | --- | --- |
| Вверх | 3 | 1 | 3 |
| Вниз | 2 | 0 | 3 |

Настройка применяется один раз к итоговому количеству после полного вычисления. В Fix сначала вычисляется заданная формула за применение, затем округляется результат. В режиме за каждый пункт сначала независимо вычисляются формулы всех учитываемых пунктов и складываются, затем округляется сумма. Например, два результата по 1,5 дают 3 ПЗ в обоих вариантах, а не 2 или 4 вследствие промежуточного округления. Предел учитываемого превышения по-прежнему действует до этих вычислений.

Настройка относится к количеству временных ПЗ. Она не меняет округление длительности, сложности проверки, характеристик или иных ресурсов. Обе подписи и название поля при реализации должны использовать ключи локализации ru/en; выбор сохраняется в конфигурации способности. Для книжного «Рвения» с суммой d6 направление округления не меняет целый результат.

**Основание и границы правил:** в [основной книге, с. 48](../../../TheWitcherTRPG-RB-Version-archive-2026-09-10/assets/books/core_rulebook.md#page-048) округление вниз указано для дополнительных параметров, а не как отдельное общее правило временных ПЗ. [«Рвение»](../../../TheWitcherTRPG-RB-Version-archive-2026-09-10/assets/books/tome_of_chaos.md#рвение-эмп) даёт сумму d6. Выбор направления здесь — согласованная возможность настройки произвольных формул; обязательное округление временных ПЗ вверх или вниз из этих правил не следует.

**Уточнение по [решению 12](#decision-12):** по умолчанию выбрано «Вверх»; явный выбор «Вниз» сохраняется. Согласно [решению 13](#decision-13), допустимость числового результата проверяет автор настройки; специальных ограничений на ноль и отрицательные значения не добавляется. Само округление вверх не превращает исходный ноль в единицу.

**Будущая приёмка:** сохранение и повторное открытие обоих вариантов выбора; Fix и режим за пункт; дробный итог, положительный итог меньше единицы и целый итог; однократное округление после суммирования, отсутствие влияния на броски отдельных костей и на длительность. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись.

### Решение 12 — Округление вверх по умолчанию

**Принято пользователем 2026-09-20; оформление 14.3.1.00132.** Значение по умолчанию для выбора округления количества временных ПЗ — «Вверх». Положительная дробь при таком выборе не превращается в ноль: 0,5 → 1; 2,5 → 3. Целое число не меняется.

Возможность явно выбрать «Вниз» по [решению 11](#decision-11) сохраняется; сохранённый выбор не заменяется значением по умолчанию при повторном открытии или применении способности. Момент округления остаётся прежним: один раз после полного расчёта и суммирования количества. Решение относится только к количеству временных ПЗ, не к длительности и другим параметрам.

**Будущая приёмка:** новая конфигурация показывает «Вверх»; явный выбор «Вниз» сохраняется и влияет на результат после повторного открытия. Обе ветки проверяются на дробном и целом итоге по решению 11. Это требования к проекту, не выполненные игровые проверки.

### Решение 13 — Допустимость числового результата проверяет автор настройки

**Принято пользователем 2026-09-20; оформление 14.3.1.00133.** Проверка того, что формула выдаёт подходящее количество временных ПЗ, относится к ответственности заполняющего конфигурацию. Специальные ограничения на нулевые и отрицательные числовые результаты в этой задаче не вводятся.

Предложение отменять создание эффекта при результате 0 или меньше отклонено. Не считать сам знак вычисленного числа ошибкой настройки, не подменять результат нулём/единицей, не вводить дополнительный минимум и не перебрасывать формулу ради положительного значения. Согласованное округление по [решениям 11](#decision-11) и [12](#decision-12) сохраняется.

Это решение касается допустимости числового результата. Задача исправления вычисления выражений остаётся прежней: выражение нужно вычислять полностью, а не частично извлекать regex/eval-разбором. Невозможность вычислить выражение не следует маскировать произвольным числом. Специальная игровая проверка положительности для этого не нужна.

Снятие эффекта при расходовании его запаса по [решению 10](#decision-10) сохраняется; оно не превращается в отдельный запрет создания эффекта по знаку исходного результата. Дополнительную механику для некорректно настроенных способностей не проектировать; правильность их наполнения контролирует автор.

**Будущая приёмка:** вычисленный числовой результат проходит согласованное округление без дополнительного ограничения снизу или отмены применения только из-за нулевого/отрицательного результата. Проверки формул должны отличать ошибку вычисления от числового результата, который автор мог задать намеренно. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись. Вопрос о специальной проверке положительности закрыт; следующий этап обсуждения касается содержательных настроек и состава данных формул.

<a id="decision-14"></a>
### Решение 14 — Выбор значения навыка или характеристики для формул

**Принято пользователем 2026-09-20; оформление 14.3.1.00134.** Для значения навыка/характеристики, используемого в формуле, предусмотреть выбор базы или действующего значения. Предложение всегда использовать действующий уровень способности вместо базового не принимается как единственный вариант; выбор принадлежит автору настройки.

Конфигурация должна различать источник — навык или характеристику — и используемое значение:

| Значение | Смысл |
| --- | --- |
| Базовое | Исходное значение выбранного навыка/характеристики без добавления его модификаторов |
| Действующее | Значение выбранного навыка/характеристики с применёнными модификаторами самого параметра по существующему расчёту системы |

Пример: способность изучена до 4, модификатор самого навыка повышает действующее значение до 6. Формула удвоения при выборе базы даёт 8, при выборе действующего значения — 12. Только бонус к броску не повышает значение навыка для формулы: существующее разделение «к параметру / к броску» сохраняется.

Этот выбор относится к источникам данных формул количества и длительности; количество далее рассчитывается в выбранном режиме Fix / за пункт и округляется по [решению 11](#decision-11). Готовые количество и срок по-прежнему вычисляются при применении, а не пересчитываются у уже выданного эффекта при каждом изменении параметров. Для ввода ссылки используется помощник по [решению 16](#decision-16); конкретную компоновку и синтаксис ссылки определить в техническом проекте. Не ограничивать механизм одним неизменным значением @level.

**Уточнение по [решению 15](#decision-15):** источником значения можно выбрать применяющего способность или получателя эффекта. Настроенный параметр получателя для сложности из [решения 01](#decision-01) этим решением не меняется; речь о доступе к значениям в формулах количества и длительности.

**Будущая приёмка:** выбрать навык и характеристику; для каждого проверить базовое и действующее значения с модификатором самого параметра, затем с модификатором только к броску. Сохранить настройку и повторно открыть её; применить формулу количества/длительности и проверить соответствующий выбранному значению итог. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись.

<a id="decision-15"></a>
### Решение 15 — Выбор участника как источника значения в формуле

**Принято пользователем 2026-09-20; оформление 14.3.1.00135.** В формулах количества временных ПЗ и длительности разрешить выбор, чьё значение используется: применяющего способность или получателя эффекта.

| Источник | Значение роли |
| --- | --- |
| Применяющий способность | Персонаж, который использует способность; например, жрец со своим навыком Рвения |
| Получатель эффекта | Персонаж, которому выдаются временные ПЗ; например, цель, характеристику которой автор настройки использует в формуле |

Выбор участника дополняет [решение 14](#decision-14): для соответствующего участника выбирается навык/характеристика и базовое либо действующее значение. При применении способности на себя обе роли относятся к одному персонажу. Роли определяются фактическим применением способности, а не тем, какой клиент технически выполняет запись эффекта.

Эта возможность относится к формулам количества и длительности. Расчёт сложности по настроенному параметру получателя и множителю из [решения 01](#decision-01) сохраняется. Значения подставляются при применении; выданные количество и срок не пересчитываются из-за дальнейшего изменения навыков, характеристик или выбранной в интерфейсе цели.

**Будущая приёмка:** задать разные базовые и действующие значения у применяющего и получателя, затем проверить оба источника и оба вида значения в формулах количества/длительности. Отдельно — применение на себя и сохранение выбора после повторного открытия настройки; использование роли получателя не должно случайно читать параметры применяющего или исполняющего запись GM. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись. Принадлежность источника согласована; способ составления формул определён в [решении 16](#decision-16), технический формат ссылок предстоит определить в проекте.

<a id="decision-16"></a>
### Решение 16 — Помощник вставки параметров в формулы

**Принято пользователем 2026-09-20; оформление 14.3.1.00136.** Для полей формул количества временных ПЗ и длительности использовать текстовое поле с помощником «Вставить параметр». Вариант только ручного ввода со справкой не выбран.

Помощник позволяет выбрать:

1. Участника: применяющего способность или получателя эффекта — по [решению 15](#decision-15).
2. Источник значения: навык или характеристику, затем конкретный параметр — по [решению 14](#decision-14).
3. Базовое или действующее значение выбранного параметра.

После выбора в редактируемую формулу вставляется ссылка на параметр. Пользователю не требуется помнить технические имена полей. В конфигурации сохраняется ссылка, а не числовое значение персонажа в момент настройки: значение подставляется при применении способности в согласованном контексте. Числа, кости и арифметические операции можно вводить и изменять вручную; помощник дополняет текстовый ввод.

Кнопка, подписи полей и вариантов выбора должны использовать ключи локализации ru/en. Конкретные обозначения ссылок, расположение элементов и взаимодействие с существующим редактором способности описать в техническом проекте. Помощник не вводит дополнительных игровых ограничений на результаты формул и не меняет ответственность автора настройки по [решению 13](#decision-13).

**Будущая приёмка:** вставить параметр в формулу количества и отдельно длительности; проверить все согласованные варианты участника, источника и базы/действующего значения. Дополнить ссылку арифметикой или костями, сохранить, повторно открыть настройку и применить способность. Изменение значения параметра до нового применения должно учитываться новой выдачей; уже выданный эффект сохраняет свои количество и срок. Проверить подписи ru/en и сохранение ручного редактирования. Это требования к проекту, не выполненные игровые проверки.

**Состояние:** решение записано; игровой код, данные и статусы шести issues не менялись. Основные варианты поведения и способ настройки согласованы; формат ссылок, хранение источников, интеграция с расчётом/доставкой эффектов и подробная программа проверок остаются работой технического проектирования.

<a id="decision-17"></a>
### Решение 17 — Полный состав навыков в помощнике

**Принято пользователем 2026-09-20; оформление 14.3.1.00137.** В формулах нужны не только характеристики, стандартные навыки и уровень применяемой способности, но и **произвольные навыки-предметы и навыки других профессий**. Предложенное ограничение состава первой реализации не принято.

Для всех навыков сохраняется выбор базового/действующего значения и роли применяющего/получателя. Имена служат подписями, а не идентификаторами: у персонажа могут быть одинаково названные навыки. Для конкретного навыка пользователь выбрал идентификатор, см. [решение 18](#decision-18). Код не менялся.

<a id="decision-18"></a>
### Решение 18 — Связывание произвольных навыков по идентификатору

**Принято пользователем 2026-09-20; оформление 14.3.1.00137.** У каждого произвольного навыка должен быть свой уникальный идентификатор. Предложение выбирать конкретный навык заново при применении не принято; проект должен предусматривать адресацию по идентификатору, без поиска по названию.

У Item уже есть UUID экземпляра, но копия у другого Actor получает новый UUID. Сохранение отдельного ID навыка у копий подтверждено пользователем в [решении 19](#decision-19). Код не менялся.

<a id="decision-19"></a>
### Решение 19 — Общий ID навыка у копий, отдельный UUID экземпляра

**Принято пользователем 2026-09-20; оформление 14.3.1.00138.** Копии одного и того же навыка на разных персонажах сохраняют общий **ID навыка**. UUID конкретного предмета остаётся отдельным у каждого экземпляра. Для навыка внутри профессии общий ID принадлежит самому навыку, а UUID — предмету профессии; при копировании профессии ID её навыков сохраняются.

Формула хранит ID навыка, роль участника и выбор базового/действующего значения. При применении этот ID разрешается среди навыков выбранного участника в его собственный Item и, для профессии, конкретный слот. Значение берётся у этого участника, а не из шаблона, по которому настраивали ссылку. Переименование не меняет ID и не разрывает ссылку. Новый самостоятельный навык получает новый ID; копирование того же навыка его сохраняет.

Пример: у персонажей А и Б находятся копии навыка с `skillId = S`, но с разными UUID и уровнями 4 и 7. Ссылка на получателя с ID `S` читает уровень 4 при получателе А и 7 при получателе Б. Одно имя при разных ID не делает навыки одинаковыми. Существующие проверки отсутствующего/неоднозначного адреса в проекте сохраняются.

Уточнение завершает сбор решений; оно внесено в контракт ссылок, .002–.004 и S13/B08. Восемь подзадач остаются запланированными; код и статусы issues не менялись.

### Контракт настройки способности и формул

Оставить текущий путь `skillUsage.temporaryHealth` и существующие поля. Дополнительные технические имена ниже — проект расширения схемы.

| Поле | Значения / начальная настройка | Поведение |
| --- | --- | --- |
| `addTemporaryHealth` | Существующий выключатель | Включает механизм у конкретной способности |
| `mode` | `fixed` / `perPoint`; по умолчанию `perPoint` | Расширяемый выбор режима, не bool |
| `requiresCheck` | Bool, начальное `true` | Редактируется для Fix; в `perPoint` проверка обязательна независимо от скрытого значения |
| `difficultyCheck.stat` / `.multiplier` | Существующие поля; `int` / `3` | Сложность по действующему параметру получателя |
| `difficultyCheck.maxRollOver` | Существующее поле; `5` | Используется только в `perPoint` |
| `temporaryHp.value` | Строка полной формулы; `1d6` | Одинаковый синтаксис констант, арифметики и кубов в обоих режимах |
| `rounding` | `up` / `down`; `up` | Одно округление после всей суммы |
| `temporaryHp.duration` | Строка формулы; `2*@p1` | Вычисляется один раз при выдаче |
| `durationUnit` | `rounds` / `minutes` / `hours` / `days`; `rounds` | Только `rounds` имеет боевой отсчёт |
| `references` | Словарь ссылок `p1`, `p2`, … | Описания выбранных параметров; начальная `p1` — базовый уровень применяемой способности |

Для «Рвения» начальные значения дают 1d6 за учитываемый пункт превышения, максимум пять пунктов, длительность — удвоенный базовый уровень способности. Это пример конфигурации, а не проверка имени профессии в коде. Проверка сохраняет нынешнее сравнение **строго больше** сложности. Критические правила существующего броска отдельно не рефакторятся.

**Предложение по ссылкам:** формула содержит короткий токен `@p1`, а `references.p1` — структурированное описание: роль `source`/`target`, адрес параметра и выбор `base`/`effective`. Например, `2*@p1+1d6` с `p1 = {role: target, target: {kind: stat, key: body}, value: effective}`. Для самой используемой способности — относительный адрес `kind: ability`, разрешаемый через уже известные Item и слот, без записанного UUID владельца шаблона. Стандартный навык адресуется ключом `CONFIG.WITCHER.skillMap`, не переводом или названием.

**Уточнение пользователя 2026-09-20:** состав помощника включает также **произвольные навыки-предметы и навыки других профессий**. Ограничение только стандартными навыками и применяемой способностью не принято. Для конкретного выбранного навыка использовать существующий контракт `resolveRollTarget`: `{kind: item, itemId}` либо `{kind: profession, itemId, path}`; путь слота — `definingSkill` или `skillPath1…3.skill1…3`. Навык и его характеристика не складываются автоматически: ссылка возвращает именно выбранное значение навыка.

**Решение пользователя по адресации:** каждый произвольный навык имеет уникальный идентификатор. Выбор конкретного навыка заново при применении не закладывается. Предлагаемый технический формат — отдельное поле `skillId` в Item-навыке и каждом слоте профессии, ссылка формулы хранит его вместе с ролью и base/effective. Реальный Item ID/слот разрешается у участника непосредственно перед вычислением; UUID владельца шаблона в формулу не зашивается.

**Согласованный контракт идентичности:** `skillId` сохраняется у копий одного навыка на разных Actor; UUID экземпляров различаются. При копировании профессии сохраняются ID её навыков. ID назначается новому самостоятельному навыку один раз и сохраняется в source; копирование, импорт уже идентифицированного шаблона, переименование, render/prepareData и перезагрузка не генерируют его заново. Формула сохраняет общий `skillId`, а Item ID и путь слота получает только при разрешении ссылки у нужного участника.

Для произвольного навыка descriptor, например, содержит `{role: target, target: {kind: item, skillId: S}, value: base}`; для другой профессии — `kind: profession` с ID её навыка. Помощник записывает ID выбранного навыка, не UUID его экземпляра. Не добавлять автоматический поиск по совпадению названия и не использовать несуществующий навык как нулевой. Совпадение имени при разных ID не считается совпадением навыка; отсутствие или неоднозначность ID обрабатываются как уже предусмотренная ошибка адреса.

Базу читать из сохранённого поля без модификаторов: характеристика — `system.stats.<key>.unmodifiedMax`, встроенный навык — `system.skills.<group>.<key>.value`, произвольный навык-предмет — `Item.system.value`, любой выбранный навык профессии — `Item.system.<slot>.level` (включая применяемую способность). Действующее значение брать из актуального результата подготовки параметра/навыка; не включать `rollModifier`, `fullExtra`, ручной бонус броска или выбранные условные бонусы к броску. Адреса текущего Item и слота поступают из контекста применения, а не от технического исполнителя доставки.

Помощник возле **каждого** поля формулы: участник → вид/конкретный параметр → база/действующее → «Вставить». Под полем показывать понятные расшифровки использованных ссылок. Сохранение токенов и descriptors — одним обновлением слота. Не перенумеровывать уже вставленные токены при открытии формы; не менять формулу при смене языка; повторное использование одной ссылки допустимо. Названия, подсказки, ошибки и кнопки — только ru/en-ключи. Ввод формулы остаётся ручным, помощник не заменяет её числом.

Вычислитель получает готовый снимок выбранных чисел и отдельную функцию броска Foundry `Roll.evaluate()`. Ни `eval`, ни вырезание части выражения regex не используются. Подставлять только известные ссылки; отсутствующий адрес/ошибку синтаксиса показывать как ошибку соответствующего поля, не подменять нулём. Корректное конечное число само по себе не отвергать из-за знака. Не вводить произвольные числовые пределы конфигурации.

- Fix: выполнить всю формулу количества один раз. При включённой проверке сначала получить успех, при выключенной не открывать окно проверки способности.
- За пункт: определить учитываемое превышение, затем **независимо** вычислить всю формулу для каждого пункта; сложить результаты. Не склеивать строки, не умножать один случайный результат на число пунктов.
- После всей суммы применить выбранный `ceil` или `floor`. Количество и длительность вычислять раздельно; настройка округления количества не округляет длительность или сложность.
- Срок и все значения формул зафиксировать до отправки AE. Ошибка вычисления не должна оставить частично выданный эффект. Число `0`/отрицательное число не является синтаксической ошибкой и не становится принудительной единицей.

<a id="design-effect"></a>
### Контракт выданного эффекта и расхода

Выдача создаёт обычный системный **base ActiveEffect** на получателе. В source используются `name`, `img` именно применяемого Item, `description`, `origin` и `system.changes`. Значение строки временных ПЗ — объект `{name, value}`, где `value` — вычисленный числовой остаток. Это **единственный сохраняемый остаток**; отдельный дублирующий ресурс Actor не создаётся.

Ключ строки: `system.combatEffects.temporaryEffects.temporaryHp.<rowId>`, где `rowId` — технический идентификатор без точек, сгенерированный независимо от подписи. Имя с кавычками, точками, обратной косой, кириллицей или переименование эффекта не меняет адрес. При чтении экземпляр источника определяется парой **UUID эффекта + ключ строки**; это отличается от `effectTypeId` семейства и идентификаторов повторной доставки. Два независимых источника с одинаковым названием не должны случайно сливаться.

Общий сборщик источников используется и уроном, и суммой на обоих листах Actor. Он читает актуальные применимые **активные** AE, включая эффекты с ручным сроком; исключает disabled/suppressed по существующей системе. Отбор строки — точный префикс/структура ключа временных ПЗ, а не `includes('temporaryHp')` и не наличие хотя бы одной похожей строки у всего эффекта. Положительный остаток доступен для поглощения; первоначальная неположительная настройка не блокирует создание и не должна превращаться в дополнительный урон.

Порядок — сохранённое время создания экземпляра `AE._stats.createdTime`, затем устойчивый UUID при совпадении времени; строки одного AE — порядок source. Обновление остатка, `sort`, переименование, перезагрузка и отображаемый срок не переставляют источники. Для незаписанных шаблонов очередь расхода не строится. Такой порядок не требует отдельного счётчика на Actor.

При уроне обычным ПЗ:

1. Снять исходное текущее значение обычных ПЗ и собрать источники; рассчитать план поглощения по FIFO до первой записи.
2. Для частично расходуемого AE скопировать **source** `system.changes`, изменить только `value.value` соответствующих строк. Не сохранять обратно подготовленные служебные поля `effect`/приоритеты и не трогать чужие изменения.
3. Если все запасы временных ПЗ этого расходуемого эффекта исчерпаны, удалить **весь экземпляр AE**, как согласовано в решении 10. При нескольких строках временных ПЗ не удалять его после первой строки, пока есть запас в остальных. Другие его модификаторы исчезают вследствие удаления, а не из-за ошибочного расхода чужих строк.
4. Только непоглощённую часть вычесть из обычных ПЗ. Если она нулевая, не наносить дополнительный урон. Урон выносливости и прочим ресурсам оставляет прежний маршрут.
5. Выполнять записи последовательно с `await`; всю локальную операцию провести внутри существующего `withParameterChanges`. Нормализация после снятия составного AE не должна сначала обрезать текущие ПЗ, а затем повторно уменьшить их из-за промежуточного состояния.

Удаляются документы эффектов получателя, не Item-источники, игровые шаблоны или компедиумы. Семейства/несуммируемость, подавление экипировкой и принятые границы одновременных действий остаются прежними. Новый протокол транзакций/отката нескольких клиентов в эту задачу не включается.

<a id="design-duration"></a>
### Локальный срок временных ПЗ

Предлагаемое поле `AE.system.temporaryHpDuration` содержит вычисленные `value`, `unit` и боевую привязку `combatId`, `combatantId`, `startRound` (до начала отсчёта — пустые). Оно **не хранит второй остаток ПЗ**. Наличие этого поля отличает выдачу по TASK-0012 от остальных эффектов с обычными нативными таймерами.

Для отмеченного эффекта нативное автоматическое истечение отключено; `WitcherActiveEffect` делегирует подготовку понятной `duration.label` и право на нативное отслеживание небольшому сервису срока временных ПЗ. В списке эффектов сохраняется понятная группировка временных выдач, включая ручной срок, без зависимости поглощения от `isTemporary`. Для остальных AE возвращается штатное поведение. Не менять глобальный `expiryAction`, `CONFIG.time.roundTime`, core-классы или мировое время. При копировании шаблона выданного эффекта не переносить привязку к старому бою; повтор доставки существующего результата не создаёт нового экземпляра.

| Ситуация | Действие |
| --- | --- |
| Минуты, часы, дни | Показать «N единиц, снимается вручную»; никаких автоматических списаний по мировому времени или завершению боя |
| Раунды, получатель вне начатого боя | Сразу выдать запас; показать полный срок и ожидание боя; никакого отсчёта по часам |
| Выдача участнику начатого боя | Привязать к его бою/участнику и текущему раунду при фактическом создании эффекта |
| Начало боя / добавление получателя в уже начатый бой | Привязать ещё не запущенные раундовые выдачи, сохранив остаток ПЗ и ранее вычисленную длительность |
| Переход раунда | Остаток срока определяется разницей раундов с сохранённой точкой старта; несколько боевых событий одного раунда не списывают его несколько раз |
| Срок исчерпан | Снять выданный AE целиком, без повреждения обычных ПЗ из-за исчезновения неиспользованного запаса |
| Завершение/удаление или сброс начатого боя | Снять раундовые AE, привязанные к этому бою, независимо от оставшегося срока; другие бои и ручные сроки не трогать |
| Перезагрузка / повторная подготовка | Использовать сохранённую привязку; не запускать срок заново, не бросать кости и не восстанавливать потраченные ПЗ |

Техническая единица отсчёта — изменение номера раунда, без дополнительной настройки ходов/секунд. Для примера: выданный в раунде 3 срок 2 раунда истекает при переходе к раунду 5. Проверить это на старте, выдаче в середине раунда и при пропуске нескольких раундов; обычные нативные turnStart/turnEnd других AE не меняются.

Регистрация обработчиков — через `module/setup/hooks.js`: переходы Combat, появление Combatant и удаление/сброс Combat; обновление/перерисовку выполняют клиенты, сохраняемые привязки/автоматические удаления — один активный GM, как в текущем контроле истечения. При `ready`/подключении GM сверить уже сохранённый срок с существующим боем, не сбрасывая старт. Для несвязанных Actor-событий не запускать обход всего мира. Временная недоступность GM не становится новым протоколом доставки или поводом дублировать обработчик на каждом клиенте.

<a id="design-delivery"></a>
### Применение и повторная доставка

`doProfessionSkillUsage` по-прежнему разрешает конкретные Item/слот и получателя. Сначала формируется контекст ролей. Если требуется — выполняется существующая проверка; после успеха вычисляются количество и срок. В Fix без проверки создаётся обычное сообщение о применении с уже вычисленным результатом; фиктивный успешный бросок навыка не нужен.

Передавать plain source AE через существующий `createEffectDelivery` и сохранённый UUID получателя. Для сообщения показать количество, вычисленный срок, источник и получателя; броски количества/длительности должны быть объяснимы по сообщению, а не существовать только в консоли. Общий шаблон карточки доставки менять лишь если его нынешних данных недостаточно для этих подписей.

При повторной отправке использовать сохранённый payload TASK-0011: смена выделенной цели, параметров персонажа или исполнителя записи не меняет сумму/срок и не повторяет кости. Боевой старт относится к фактической выдаче, а не к моменту неудачной отправки. Успехи/отказы/ручное завершение, права GM/владельца и идемпотентность доставки остаются действующими; TASK-0012 не строит вторую систему сетевых подтверждений.

### TASK-0012.009 — Доступные настройки всех навыков профессии

**Факт:** у новой профессии уже есть десять `skillId`. Общая вкладка редактирует `system.definingSkill.skillId`, а не ID профессии. `_prepareTabs` заменяет подписи трёх веток пустыми `pathName`; нативные ссылки вкладок получают высоту 0. При чтении реального окна обнаружены все десять полей ID; вкладки веток имели размер 10×0 px. Общий `.profession-card { max-width: 400px }` одновременно сжимает форму даже при растягивании окна. Предыдущие тесты использовали именованные ветки и этот случай не покрыли.

**Проект решения:**

1. Сохранить нынешние пять вкладок. Для профессии подписывать `general` как «Основной навык», пустые или состоящие из пробелов названия веток показывать как «Ветка 1», «Ветка 2», «Ветка 3». Непустые авторские названия остаются названиями вкладок. `data-tab` и адреса данных не меняются.
2. В каждой карточке показывать структурную подпись: «Основной навык» либо «Навык 1/2/3» внутри выбранной ветки, плюс заданное имя навыка при его наличии. Пустое имя не должно оставлять безымянный блок. Резервные подписи строятся в контексте формы, не записываются в `skillName/pathName`.
3. Рядом с полем ID дать краткую подсказку: это идентификатор конкретного навыка для ссылок в формулах; копии навыка сохраняют его, UUID экземпляров предмета различаются. Не регенерировать ID при render, именовании ветки, открытии вкладки или копировании. Для старого пустого ID сохранить существующую явную кнопку назначения.
4. Выделить класс только для конфигурации профессии. Предлагаемый базовый размер — 800×700 px с ограничением доступной областью экрана. Содержимое вкладки прокручивается, навигация остаётся доступна; заголовок «Настройки» получает компактный размер около 20 px только в этом окне.
5. В пределах нового класса снять ограничение карточки 400 px, расположить три навыка вертикальными самостоятельными блоками. На обычной ширине подпись поля занимает примерно 280 px, поле/чекбокс — остальное; межколоночный отступ 16 px. Длинные пояснения переносятся целыми словами. При ручном сужении окна форма переходит в одну колонку, а не сдавливает подписи до одного слова в строке. Основной лист профессии и конфигурации остальных Item не затрагиваются глобальным переопределением.
6. Все новые служебные подписи и подсказки добавить через ключи ru/en. Структура данных, генератор ID, формулы и выбор навыков по ID остаются прежними.

<a id="task-0012010"></a>
### TASK-0012.010 — Подтверждение первой записи травмы с эффектом

**Факт:** новая травма и её штраф сохраняются, но `stageMatches` сравнивает ожидаемый `effects[].start = null` с заполненным в `_preCreate` объектом часов и возвращает `failed/uncertainWrite`. Это воспроизведено последовательно одним клиентом, отдельно от принятого ограничения одновременной выдачи травмы двумя клиентами. В сравнении запроса и результата других расхождений проверяемых полей не обнаружено; ownership добавляется ядром и уже не входит в сравнение.

**Согласованный проект, уточнение .00144:** в ветке первоначального создания `writeStage`, после подготовки нормализованной копии стадии и перед вызовом create, заполнить отсутствующий `start` каждого вложенного AE существующим `initializeEffectStart(effect, actor)`. Подготовленные `start` и `duration` входят и в отправляемые данные, и в ожидаемую стадию. Исходный шаблон не меняется. Уже заданный `start` helper сохраняет. При внутреннем создании травмы `WitcherItem.createDocuments` передаёт в `assignedItemData` опцию `preserveEffectStart: operation[WOUND_INTERNAL] === true`. Только уже подготовленные часы сохраняются; при null start действует обычная инициализация. Внешний импорт по-прежнему сбрасывает старый start и expired. Назначение порядка несуммируемых источников выполняется независимо от сохранения часов. Вложенный AE._preCreate при создании Item не вызывается — защиту обеспечивает именно этот контракт общего обработчика.

Не убирать start/duration из `stageMatches`, не сравнивать результат с копией самого сохранённого Item и не объявлять любое наличие Item успехом. Полное сравнение изменений/флагов/эффектов, количество созданных документов и единственность травмы остаются условиями успеха. Сбой записи, отмена hook, отсутствующий/лишний AE, изменённый штраф или неожиданные часы продолжают возвращать ошибку. Ветку замены существующего Item и правила сброса стадии не менять в этом исправлении.

**Файлы реализации:** [criticalWoundOperations.js](../../module/item/criticalWoundOperations.js) готовит ожидаемые часы перед первым create; [witcherItem.js](../../module/item/witcherItem.js) передаёт признак внутреннего создания; [effectFamilies.js](../../module/activeEffect/effectFamilies.js) сохраняет подготовленный start/duration, продолжая назначать порядок семейств. Два последних изменения согласованы после игровой проверки .00142. [effectApplication.js](../../module/activeEffect/effectApplication.js), [witcherActiveEffect.js](../../module/activeEffect/witcherActiveEffect.js), damageMixin и обработчики лечения — зависимости для проверки; их код в дополнении не меняется.

**Локальные проверки:** создание без AE, с одним/несколькими AE; null и явно заданный start; вне боя, до/на/после хода получателя, turnStart/turnEnd. Сопоставить точные ожидаемые часы и длительность, подтвердить однократную коррекцию. В стенде пройти настоящий `WitcherItem.createDocuments → assignedItemData`, явно отметить подменённую БД. Вызов вложенного `_preCreate` не подставлять вместо настоящей цепочки; отдельное создание AE проверить как смежный сценарий. Дополнительно проверить отмену/исключение create, пропавший AE, изменённые `system.changes`, duration/start, дубликат травмы: ошибочный результат по-прежнему обнаруживается. Повтор травмы, ручная замена и лечение сохраняют прежний UUID и результаты. Шаблон после всех операций равен исходному.

**Браузерная приёмка:** у character и monster впервые получить из настроенного компедиума травму ноги с эффектом — через игровой `applyCritWound` и ручное перетаскивание. Проверить `applied`, отсутствие ложного уведомления, одну травму, фактический штраф, сырой start и сохранение после reload GM/Player. Повторно получить ту же травму, стабилизировать/лечить и вручную заменить стадию; проверить прежние ограничения постоянных последствий. В бою проверить часы AE отдельно от временных ПЗ. Запрет записи проверять контролируемым hook в QA с обязательным снятием hook, не повреждением игровых данных.
