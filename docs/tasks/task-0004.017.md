## Связи и порядок проверки

1. Сопоставить все 128 экспортов с манифестом, моделью RollTable/TableResult, UUID, формулами, range/replacement/drawn и графом 254 известных ссылок; пересчитать фактический состав.
2. Разделить прямой roll, рекурсивный draw, нормализацию, вывод описания/inline и переход к документу. Для каждого пути определить настоящий потребитель, а не только похожее имя.
3. Проследить основные генераторы, семейные/возрастные подтаблицы и ограничение глубины; сохранить параметры входа при переходе в дочерний Roll и границу, на которой они теряются.
4. Сопоставить Combat с кодом локации/критической травмы (.010/.012): текстовая таблица может быть только ручным справочником.
5. Проверить checkIfItemHasRollTable и экспорт добычи (.006/.013/.014): ожидания по имени, типу результата и UUID должны совпадать с данными.
6. Использовать .052–.057/.061 для проверки применимости всех 995 результатов и 51 inline; пакетные проверки структуры дополнить разбором каждого исключения.
7. Проверить отсутствующие цели, циклы, неоднозначные диапазоны и недостижимые результаты. Не корректировать контент по рулбукам и не запускать compile/extract.

## Внутренние этапы

1. Общий граф/манифест и обычные таблицы.
2. Составные генераторы и глубина — по отдельным входным ветвям.
3. Боевые таблицы, добыча и передача результата интерфейсу.

После каждого внутреннего этапа записать проверенные файлы и связи, выводы, использованные старые доказательства и новые проверки. Если поздний потребитель меняет понимание ранее разобранного источника, уточнить обе карточки и соответствующую строку общей матрицы. Следующий номер задачи сам по себе не является программной зависимостью.

## Контрольные случаи

- Две отсутствующие ссылки Mounted Control Loss и пересечение Monster на 9 — сопоставить с актуальным кодом потребителя.
- xN в inline, глубокая цепочка, потерянный возрастной модификатор и повторный draw.
- Текстовый результат на маршруте генерации Item; одинаковое имя и несколько подходящих пакетов.

Это план проверки, а не заранее установленный результат. Для нового исполнения использовать настоящую модель/метод и фактически проверенную версию ядра; ожидание обосновывать контрактом вызывающей стороны. Где достаточно повторного чтения неизменённого кода и применимого протокола, указать это явно. При недоступной границе сузить вывод и записать точный непроверенный вопрос.
