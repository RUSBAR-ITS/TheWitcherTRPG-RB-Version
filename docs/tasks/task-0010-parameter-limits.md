## Назначение и граница с травмами

Спроектировать общий рефакторинг параметров и модификаторов из любых источников: рас, предметов, травм и других эффектов. Значение параметра, допустимый предел, поправка к броску и вклад в производные величины должны иметь явные роли. Травмы — один из источников эффектов, не место реализации общей арифметики.

Из TASK-0009 сюда перенесены **issue-00036**, материалы М08, числовая контрольная точка К03, проверки I10/B09 и С13/Б11. Они не выполнены и не закрыты. Рефакторинг общего вычисления больше не является условием завершения переходов/повторов/заживления в TASK-0009; приёмка травм обязана явно сохранять ограничение о численно неисправных эффектах до этой работы.

В TASK-0009 остаётся согласованный потребитель: срок заживления динамически вычисляется по **действующему Телосложению с модификаторами**, прошедшие дни не сбрасываются. Эта задача должна предоставить согласованное действующее значение, не меняя вручную правила отдельных травм.

## Требования пользователя для следующего обсуждения

Ниже закреплены направления/свойства, которые необходимо рассмотреть. Это не выбранные schema, фазы Foundry, порядок операций или готовые ограничения всех полей.

| Требование | Что должно быть рассмотрено |
| --- | --- |
| Минимальное значение параметра — **1** | Нижняя граница значения параметра и область её применения. Отдельно определить отношение к текущим запасам ресурсов, нулю ПЗ/STA и порогам смерти |
| Обычное максимальное значение параметра — **10** | Базовый потолок и таблица применимости к видам параметров. Это не автоматическое ограничение ёмкости HP/STA десятью: они вычисляются в другой шкале |
| Эффект **сдвигает максимум**, свойство bool | Например, расовый бонус влияет на допустимый потолок. Величину сдвига и взаимодействие с величиной самого бонуса определить при проектировании |
| Влияние на **бросок**, отдельно от значения параметра | Ограничение параметра снизу не должно само по себе обрезать полный штраф к броску. Нужен также вариант модификатора, влияющего только на бросок и не меняющего параметр |
| Эффект **не участвует в пересчёте производных**, свойство bool | Исключение вроде снижения BODY, которое не должно уменьшать HP. Определить область исключения: все производные либо конкретные зависимости; не отключать автоматически влияние на все ресурсы |
| Собственные модификаторы производной величины | После/в составе вычисления основы HP/STA учитывать их собственные эффекты, включая пример +10 STA и ×0.25; порядок ещё обсуждается |
| Конфигурируемость | Свойства доступны через существующий редактор/мастер ActiveEffect; не создавать зашитую таблицу правил по именам/ID рас или травм |

Нужно различать **рассчитанный максимум ресурса** (`derivedStats.*.max`), **допустимый потолок параметра**, **действующее значение** и **текущий запас**. Совпадающее слово «максимум» не делает их одним полем. Никакой clamp 1/10 для всех ресурсов на этом шаге не вводится.

## Вопросы для следующего этапа

1. Какие семейства параметров имеют границы 1/10, какие — иные правила; где сохраняется возможность нулевого/отрицательного текущего запаса?
2. На каком уровне хранить свойства: отдельная строка changes/модификатор или весь ActiveEffect с несколькими изменениями? Не навязывать общую галочку всем бонусам многокомпонентного эффекта без обсуждения.
3. Как вычисляется изменение потолка: тот же бонус/отдельная величина, положительные/отрицательные значения, множители, несколько источников?
4. Как одновременно представить модификатор параметра и полный штраф броска, не посчитать его дважды; какие режимы bool/выбора нужны в редакторе?
5. Что именно исключается из производных: весь эффект либо его изменение конкретного параметра, для всех потребителей или например только HP? Как сохранить другие модификаторы этого же BODY?
6. Порядок сложения/умножения/деления, лимитов и округления; взаимодействие со штатными mode/priority, фазами initial/final, выключением/подавлением/transfer. Не переносить автоматически все changes в final.
7. Общая зависимость BODY/WILL → HP/STA и её исключения: результат сердца 10/6 пока не выбран. Особое правило одного ранения не должно становиться неявной моделью всех производных.
8. Когда пересчитывается ёмкость и что происходит с текущим запасом при её уменьшении/восстановлении? Подготовка данных не должна незаметно лечить или тратить ресурс.
9. Как показывать исходное значение, модификаторы, потолок, итог параметра и отдельную поправку броска, чтобы результат можно было проверить?

### Сохранённый проект М08

**Историческая граница М08:** прежний проект отдельно исключал новые лимиты/потолки. С .00039 его вопросы рассматриваются вместе с ними в TASK-0010; пункты ниже — сохранённый вариант исследования, а не утверждённый алгоритм нового рефакторинга.

1. До кода выписать числовой контракт для `unmodifiedMax` (база), подготовленного `max`, используемого `value`, totalModifiers и initial/final; отдельно основные характеристики и ресурсы. Зафиксировать исходное поведение без эффектов, customStat, ранения/нагрузку. Поле max не означает потолок разрешённого бонуса.
2. Для основных характеристик предлагается использовать уже изменённый initial-эффектом max как базу calculateStat, сохранив существующие totalModifiers, штрафы и делитель. Подготовка должна оставаться идемпотентной при двух calculateStats и повторном prepareData; исходный unmodifiedMax не переписывается.
3. Для производного max сначала получить его вычисляемую базу, затем применить относящиеся к нему изменения ровно один раз до использования потребителями. Предлагается адресный этап обработки таких целей с сохранением типов, priority, активности, transfer и явно выбранной final-фазы. Точный способ включения в цикл Foundry утвердить после числовой матрицы: не повторять целиком initial/final applyActiveEffects (ядро запрещает повтор фазы), не переносить весь многокомпонентный эффект в final.
4. Контрольная точка: Heart Damage одновременно меняет BODY и STA. При BODY/WILL=8 исходная STA=40; нужно явно согласовать, четвертится ли исходная ёмкость или база после изменения BODY. Аналогично проверить септический шок с изменённой WILL. Текст о четверти подтверждает потерю эффекта, но сам по себе не описывает порядок программного пересчёта. Не закреплять произвольный итог тестом.
5. Независимые установленные ожидания: SPD 8 при ×0.25 даёт рабочее значение 2, при ×0.5 —4; RUN, использующий SPD, соответственно6/12 без других поправок.
