<a id="requirements"></a>
## 1. Принятый контракт и границы

Настройки численного воздействия принадлежат **отдельной строке изменения ActiveEffect**. Источниками могут быть раса, профессия, травма, предмет, статус. Общий расчёт не проверяет названия/ID конкретных рас или травм. Идентичность и запрет повторного суммирования относятся к эффекту целиком.

| Настройка | Согласованный смысл |
| --- | --- |
| «К параметру» | Меняет действующее значение характеристики/навыка либо соответствующую числовую цель |
| «К броску» | Меняет только подходящую проверку; не меняет параметр, его производные или цену прокачки |
| Совместимость каналов | «К параметру» и «К броску» взаимоисключающие; оба могут быть выключены |
| «Полный эффект» | Только для «К параметру»: не поместившаяся из-за минимума/потолка часть **бонуса или штрафа** учитывается в броске |
| «Сдвиг потолка» | Отдельная настройка, действует в обе стороны и использует величину/операцию строки. Разрешена с «К параметру» и без обоих каналов; недоступна с «К броску» |
| «Влияет на прокачку» | Отдельная настройка для расчёта цены/доступности повышения; возможна и без обоих каналов. Недоступна с «К броску» |
| Ни одного действия | Если выключены оба канала, сдвиг потолка и влияние на прокачку, строка не даёт численного вклада |
| «Выбирать при броске» | Для поправки к броску: игрок выбирает применимость фиксированной величины. Каждый **новый** бросок открывается с выключенными галочками |
| «Не учитывать при расчёте» | Необязательный мультивыбор производных, исключающих именно эту строку, а не весь эффект/все изменения исходной характеристики |
| Пределы | Характеристики: минимум 1; навыки: исходно 0, действующее значение может стать отрицательным. Обычный потолок 10, базовый потолок настраивается отдельно для характеристики/навыка |
| Ресурсы | Текущие HP/STA и другие запасы — не уровень характеристики. Универсальные пределы 1/10 на них не распространяются |
| Повтор эффекта | Ручной ID типа; если «Не суммируется» включено, ID обязателен. Повтор заменяет предыдущий экземпляр и начинает длительность заново |

Новые численные строки: «К параметру» включено; «К броску», «Полный эффект», «Сдвиг потолка», «Влияет на прокачку», «Выбирать при броске» выключены; список исключений пуст. Это defaults нового редактора, **не команда молча присвоить такую механику всем существующим численным changes**. Имеющиеся цели предварительно классифицируются в .010.

Вне объёма: контроль стартового предела навыков 6, режим генерации персонажа, автоматическое определение дистанции по карте, межперсонажные формулы, автоматические перебросы/лимиты их использования. «Приказ» и подобные ситуативные воздействия остаются доступны через ручной модификатор. Начисление токсичности отложено в [TODO](../todo.md), отдельная задача здесь не создаётся. Обратная совместимость со старыми данными/миграциями не требуется; сохраняется работоспособность актуального контента и штатных типов эффектов Foundry.

## 2. Хранение и редактор

Технические имена ниже — контракт модели, реализованный в .003; подключение потребителей отмечено в результатах следующих стадий. Расширяется `system.changes[]` модели системного ActiveEffect; свойства копируются и удаляются вместе со строкой. Словарь по имени эффекта/индексу строки не нужен.

| Поле проекта | Тип / default | Валидация |
| --- | --- | --- |
| `key`, `type`, `value`, `phase`, `priority` | Штатные поля Foundry 14 | Сохранить определения ядра; не возвращаться к устаревшему `mode` |
| `affectsParameter` | bool / true | Взаимоисключающее с `affectsRoll` |
| `affectsRoll` | bool / false | Запрещает cap/progression/full/exclusions для этой строки |
| `fullEffect` | bool / false | Доступно только при `affectsParameter` |
| `shiftsCap` | bool / false | Независимо от `affectsParameter`; запрещено при `affectsRoll` |
| `affectsAdvancement` | bool / false | Независимо от `affectsParameter`; запрещено при `affectsRoll` |
| `optionalOnRoll` | bool / false | Только для канала броска; выбор не меняет значение параметра |
| `excludedDerived` | массив ключей / [] | Для параметрического влияния; закрытый список существующих производных и BODY-урона |
| `system.effectTypeId` | строка / пусто | Ручной ID семейства целого AE; не заменяет `_id`, UUID или системный `type` |
| `system.nonStacking` | bool / false | При true непустой `effectTypeId` обязателен |
| `baseCap` у характеристики/навыка | число / 10 | Отдельно от текущих `max`, `unmodifiedMax`, запаса ресурса; применяется только к поддержанным целям |

Противоречивые комбинации запрещать схемой/валидацией, а не только скрытием элементов. Переключение канала должно явно приводить настройки к допустимому состоянию; импорт неверных данных не должен давать скрытое воздействие. Пустой ID при запрете суммирования — ошибка сохранения. Для нечисловых изменений, Item/Token и специальных AE сохранить их собственные схемы/операции, не навязывать им новые численные flags.

Редактор: существующая вкладка «Изменения», добавление строки и «волшебная палочка» остаются. В раскрываемой части строки размещаются новые настройки; групповой выбор копирует свойства во все созданные строки. В системной вкладке AE — ID типа и запрет суммирования. В редакторах характеристик/навыков — базовый потолок с пояснением, что это не действующее значение. Подписи/подсказки ru/en; названия параметров брать из моделей/`CONFIG.WITCHER`, а не дублировать словарём пользователя.

Foundry 14.367 разрешает заменить схему changes, сохранив `type/phase/priority` (`common/data/active-effect.mjs`). Native лист жёстко рендерит свою строку через `_renderChange`: одного изменения `PARTS.templates` недостаточно; нужен системный шаблон строки и обработка submit. Приоритет, фаза, значение и соседние строки должны переживать мастер/сохранение/reload без потерь.

<a id="calculation"></a>
## 3. Общий численный расчёт

Разделить исходное сохранённое значение, действующее значение, допустимый потолок, значение для прокачки и вклад в бросок. Нынешнее `max` — не новое поле потолка; для ресурса это ёмкость, для основной характеристики — подготовленное значение. Не переиспользовать один mutable `max` для всех смыслов.

1. Собрать действующие строки с источником, адресом цели, операцией и настройками; учитывать disabled, suppression, transfer, экипировку и фазу. Промежуточные `totalModifiers`/`activeEffectModifiers` могут остаться представлением результата, но не единственным источником данных: они теряют происхождение строки.
2. Развести каналы: собственное значение, потолок, прокачка, бросок и вход для конкретной производной. Строка с несколькими разрешёнными действиями участвует по одному разу в каждом соответствующем расчёте.
3. Для численного значения выполнить сложение/вычитание, затем умножение/деление. Деление может представляться штатным множителем 0.5/0.25; отдельный тип операции ради него не обязателен.
4. После арифметики применить замену значения с наибольшим приоритетом. Не брать первую найденную замену. При равных приоритетах сохранить детерминированный порядок ядра, без зависимости от локализованного имени.
5. Округлить вниз **один раз в конце расчёта данного параметра**, затем применить его границы. Не округлять среднее BODY/WILL до умножения на 5. Сдвиг потолка вычислять из `baseCap` операциями строк с `shiftsCap`, также без промежуточного округления. Эффективный потолок характеристики не может отменить её минимум 1.
6. Полный эффект переносит в бросок только относящийся к нему остаток после ограничений; уже вошедшая в параметр часть второй раз не прибавляется. Обычные модификаторы не становятся полными из-за соседней строки.
7. Для производной вычислить её базу по допустимым входам и применить её собственные строки по той же арифметике. Завершённый родительский параметр и его округление — вход следующей формулы, а не повод повторять всю подготовку Actor.

Таблица операций для собственного значения/потолка/прокачки должна быть общей. ADD, MULTIPLY и OVERRIDE покрываются новым контрактом. Остальные штатные операции Foundry, зарегистрированные CUSTOM и нечисловые changes не удаляются и не переопределяются случайно: до подключения вычислителя .002 проверяет их реальные типы/приоритеты и отделяет нативный путь. Если для комбинации новой настройки с такой операцией нет однозначного смысла, её нельзя молча трактовать как ADD; это отдельная контрольная точка реализации, а не разрешение менять механику.

| Случай | Ожидаемый результат |
| --- | --- |
| 7, затем ÷2 и ×2 | 7, а не 6 |
| 8, +2 и ÷2 | 5 |
| 6, +2, затем OVERRIDE 4 | 4, после чего действуют границы |
| Потолок 10, сдвиг +2 / −2 / ×2 / ÷2 | 12 / 8 / 20 / 5 соответственно |
| 10/10, +2 к параметру, без сдвига, full=true | Параметр 10, остаток +2 в броске |
| 9/10, тот же +2 | Параметр 10, остаток +1 |
| 3, −5 к параметру, min=1, full=true | Параметр 1, остаток −3, суммарный вклад −2 |
| Тот же штраф, full=false | Параметр 1, остатка нет |
| 3, −5 только к броску | Параметр 3, вклад −2; производные прежние |

**Смешанный случай согласован пользователем, .00056:** база 9, потолок 10, одновременно действуют обычный +2 и полный +2; ни один не сдвигает потолок. Итог: параметр **10**, дополнительная поправка **+2**, суммарный вклад в бросок **12**. Обычный бонус ограничивается потолком; полный сохраняет весь свой вклад. Эффекты могут быть разными и назначенными в разное время: проверяется их совместное действие, а не совпадение времени создания. Результат не должен меняться при перестановке порядка назначения этих двух ADD-бонусов. Этот результат входит в обязательный сценарий С06; числовая развилка закрыта.

Подготовка должна быть чистой и идемпотентной: повторный prepare не меняет `_source`, не тратит ОУ, не начисляет ресурс и не накапливает модификаторы. Нативные initial/final нельзя повторно запускать целиком: ядро отмечает уже выполненные фазы. Нужна адресная маршрутизация численных целей через системный вычислитель (`shouldApplyChange`/существующие точки lifecycle), с сохранением остальных строк и статусов AE. Final-строка должна примениться ровно один раз после расчёта своей цели и до её согласованных потребителей; нельзя в конце глобально испортить уже рассчитанную зависимость. Регрессионные тесты подтверждают это на настоящем lifecycle Foundry.

Состояния здоровья, нагрузка и броня остаются явными источниками существующих штрафов; их нельзя потерять или удвоить при замене проходов. Повторное вычитание перегруза00035 включено в .004; источники EV00254/00277 остаются в TASK-0011. Другие несвязанные ошибки этих механизмов не исправлять автоматически. Если сохранение текущего результата конфликтует с согласованным новым контрактом — показать конкретный случай пользователю, а не включать попутный багфикс.

<a id="progression"></a>
## 4. Прокачка и сохранённая база

`Влияет на прокачку` — самостоятельное действие строки. Для цены брать исходный приобретённый уровень и только отмеченные модификаторы; не брать подготовленное значение вместе со всеми проклятиями. Повышение записывает +1 в приобретённую базу, а не `prepared + 1`.

Цена навыка — `max(значениеДляПрокачки, 1) × множительСложности`. Каждый шаг ниже первого уровня стоит как приобретение нового навыка: обычный 1 ОУ, сложный 2 ОУ. Цена характеристики — `max(значениеДляПрокачки, 1) × 10`. При достижении предела действие повышения не должно списывать ОУ.

**Цена и доступность — разные проверки.** Параметрический положительный бонус способен довести действующий показатель до потолка и запретить повышение даже без влияния на цену. Бонус только к броску этого не делает. Неотмеченный отрицательный штраф не разрешает покупать базу сверх обычного потолка. Отмеченный штраф разрешает отрабатывать снижение повышениями, в том числе с временным приобретённым уровнем выше обычного потолка.

| Пример | Цена и предел |
| --- | --- |
| База навыка 6, расовый +2 с влиянием на прокачку | Следующий уровень стоит 8 ОУ (обычный навык) |
| База 6, −2 с влиянием / без влияния на прокачку | Цена 4 / 6 ОУ |
| Навык −2 → −1 → 0 → 1 → 2 → 3 | Обычный: 1, 1, 1, 1, 2 ОУ; сложный: удвоение |
| Характеристика, база 3, штраф −5 с влиянием | Пока база растёт 3→4→5→6→7, цены 10 за шаг; действующие значения 1→1→1→1→2. Следующий 7→8 стоит 20 |
| Та же база 3 и штраф −5 без влияния | Действует 1, повышение 3→4 стоит 30 ОУ |
| База 6, отдельное влияние на прокачку +2, оба главных канала off | Параметр/вклад 6, обычный потолок 10, цена 8 ОУ |
| База 8, +2 к параметру, cap=10, без влияния на прокачку | Действует 10: повышение закрыто. При +2 только к броску — открыто |
| База 8, −2 к параметру, без влияния на прокачку | Действует 6; повышения стоят 8, затем 9 ОУ; при базе 10 дальше нельзя, действует 8 |
| База 8, −2 к параметру и прокачке | Действует 6; повышения стоят 6, 7, 8 ОУ: база доходит до 11, действует 9 |
| Снятие предыдущего штрафа при базе 11 | Сохранённая база **обрезается до 10**, а не прячется под отображением 10. Повторный −2 даёт 8, не 9 |

Обрезание базы — явная сохраняемая операция при прекращении соответствующего воздействия/утрате допуска, отдельно от prepare. Учитывать реальную смену активности: удаление/отключение, suppression/экипировку, замену источника. Не обрезать временно допустимую базу при каждом рендере, не возвращать потраченный опыт автоматически. Проверять завершённое изменение набора эффектов, чтобы промежуточное удаление при замене не уничтожало базу до появления нового эффекта.

Текущий `levelUpSkill` читает подготовленный `skill.value`; свойства мастера эффектов обычно попадают в `activeEffectModifiers` отдельно. В имеющемся редакторе характеристик есть ручная запись, готового аналога `levelUpSkill` для характеристики не найдено. Для реализации контракта предусмотреть общую проверку стоимости/доступности и действие повышения в её редакторе. Ручное редактирование мастером и автоматическая покупка за ОУ — разные входы. Item-навыки/профессиональные навыки сверять по их фактической модели, не притворяться, что все они лежат в `system.skills`.

## 5. Производные и исключения

Список целей: `hp`, `sta`, `rec`, `stun`, `enc`, `run`, `leap`, `woundTreshold`, `resolve`, `focus` и логическая цель «Урон от Телосложения» (прибавка BODY и базовые формулы кулака/пинка). Техническое написание существующего `woundTreshold` не переименовывать. Для HP/STA речь о максимальной ёмкости. Срок заживления не становится новой галочкой: он продолжает использовать действующее BODY по TASK-0009.

| Входы | Расчёт / граница |
| --- | --- |
| BODY, WILL | HP/STA: `((BODY + WILL) / 2) × 5`, округление в конце; REC/STUN/порог ранения — свои существующие назначения |
| BODY | ENC и BODY-урон; срок заживления — существующий внешний потребитель |
| SPD → Run → Leap | Run = SPD ×3; Leap = Run/5. Прямой бонус Run участвует в Leap, если не исключён |
| INT, WILL | Resolve/Focus; адресные исключения работают отдельно для каждой цели |
| Ручной `customStat` | Ручная база заменяет формулу автоматического максимума; собственные модификаторы максимума продолжают действовать |

Для производной пересчитать вход без исключённых строк. Не вычитать строку из уже округлённого/ограниченного результата. Не выключать другие строки того же AE. Собственные модификаторы производной применяются после получения её базы.

**Цепочки:** исключение действует на соответствующем ребре зависимости и не возвращается через следующий узел. SPD5 +5 с исключением Run даёт SPD10, Run15, Leap3. Нельзя для Leap снова вычислить гипотетический Run30, забыв исключение на предыдущем шаге. Прямой Run+5 без исключений даёт Run20, Leap4; с исключением Leap — Run20, Leap3. При исключении конкретной строки из более дальней цели сохраняются также исключения на промежуточных шагах. Для этого нужны исходные строки и происхождение вкладов, а не только готовая сумма.

| Пример | Проверяемые числа |
| --- | --- |
| BODY8/WILL8, BODY −2 с исключением HP и другой BODY +2 | Действующий BODY8; вход HP использует BODY10 → HP45; STA40 |
| BODY7/WILL6, без эффектов | HP/STA32; прежние 30 из промежуточного округления не сохраняются |
| Сердце: BODY8/WILL8, BODY÷4 исключён из STA, отдельный STA÷4 | BODY2, STA10. По настройке без исключения получилось бы 6; штатные данные должны использовать вариант 10 |
| Ручная база HP100, формула без customStat дала бы50 | BODY-бонус не меняет базу100; отдельно HP+10 →110; отдельно HP×0.5 →50 |

Исключение сердца из STA не выключает влияние BODY на все остальные производные и не устанавливается всем временным эффектам автоматически. Числа настраиваются в строках компедиума, а не условием по имени травмы в Actor. Для септического шока и остальных многокомпонентных эффектов .010 составляет аналогичную матрицу по описаниям; не закреплять случайный двойной пересчёт тестом как правило.

<a id="rolls"></a>
## 6. Обычные проверки, обратные испытания и галочки

Общий сборщик получает явный контекст Actor, фактической характеристики, навыка/группы и вида проверки. Он возвращает автоматические поправки, остаток полного эффекта и подходящих условных кандидатов. Один модификатор не считается дважды при совпадении нескольких признаков. Не добавлять повторный глобальный сбор в `extendedRoll`: сегодня многие вызывающие методы уже включают эффекты в формулу.

Обычная проверка использует действующий параметр и свои поправки. В обратном испытании положительный бонус **увеличивает порог**, отрицательный уменьшает: порог6 с +2 становится8, с −2 становится4. Строгость сравнения сохраняется по виду обратного испытания (`<` либо `<=`); правила обычных атак/защит не заменяются правилом автопровала. Для обратных испытаний действует согласованная ниже граница00196; за её пределами существующие критические правила сохраняются. Применимость к Death Save определяется его собственной целью, не любым бонусом навыка.

Галочки условных строк показываются после выбора реального навыка/действия; новый бросок начинает с выключенных. При смене контекста список обновляется. Выбор не меняет AE, характеристику или длительность. Отмена не создаёт дополнительного расхода/сохранённого выбора. Если кандидатов нет, лишнее обязательное окно не требуется. Произвольный ввод бонуса сохраняется отдельно.

Входы: встроенный навык, Item-навык, профессиональная проверка/атака, атака оружием, защита/замена навыка, заклинание, обе стороны словесной дуэли, крафт/алхимия/ремонт, испытания характеристики и смерти, подходящие проверки расследования. Броски урона/таблиц/случайной длительности не становятся проверками навыка только из-за общего `extendedRoll`.

«Максимальная дистанция»: игрок выбирает обычную категорию дистанции и при необходимости условную компенсацию. Существующие +5/−2/−4/−6 остаются; карта автоматически не измеряется, величина компенсации не ограничивается новым детектором условий. «Доверие» предлагается для Харизмы/Соблазнения/Убеждения; условие цели подтверждает игрок.

<a id="automatic-failure"></a>
### Итоговый порог и автопровал — issue-00196

Согласовано пользователем в .00058. Сначала вычислить **итоговый** порог T со всеми применимыми бонусами/штрафами, включая выбранные условные строки. Затем для обратного испытания определить исход:

| Условие успеха | Граница автопровала | Пример за границей |
| --- | --- | --- |
| Результат `<= T` | `T <= 0` | При T=1 результат1 успешен |
| Результат `< T` | `T <= 1` | При T=2 результат1 успешен, результат2 — провал |

Это граница **испытания**, а не минимум характеристики: порог не поднимать искусственно до1. При автопровале итог всегда `success=false`; критическая обработка/полученный0 не должны превращать невозможную проверку в успех. Чат и возвращённый результат должны согласованно показывать провал. За пределами автопровала сохраняются текущие правила критов и сравнения конкретного вида проверки. Изменение самого порога вне броска не объявляет персонажа умершим и не меняет его ресурсы.

Отсутствие порога задаётся отдельно от числа, в частности от−1. Технический проект: null означает «не задан», конечное число — реальный порог; проверить схему и всех вызывающих потребителей в .002/.007–.008. Одной замены условия в extendedRoll недостаточно: defaults rollSkill/rollSkillCheck и другие места, использовавшие−1 как маркер, нужно перевести одновременно. Отсутствие порога не выдаёт success/failure; реальные0/−1 не теряются. Строгость брать из контекста проверки, не из знака T. Новую границу не применять к обычным броскам «выше СЛ», урону или таблицам.

**Уточнение .00059:** упоминание критической ветви здесь описывает существующий код, а не правило для испытаний. У штатных STUN/Death Save уже стоит showCrit=false; общий Stat Save и узнавание по Репутации допускают криты. Их применимость и разделение showCrit на механику/отображение исследуются отдельно в [TASK-0013](task-0013-critical-rolls.md). Защитный случай С30 с legacy-критическим0 не означает, что добросы разрешены правилами. TASK-0010 не получает попутный общий рефакторинг критов.

Пример порядка: предварительный T=0, подтверждённый бонус+2 → итоговый T=2; строгое испытание уже допускает успех на1. Поэтому нельзя запускать автопровал до сбора бонусов или при открытии окна. Числовая матрица С30 проверяет оба сравнения, границы и отсутствие порога.

## 7. Сохраняемые операции: ресурсы и повтор эффекта

**Запас ресурса:** при уменьшении максимума текущий запас обрезается только сверху до нового максимума; если он ниже, сохраняется. При увеличении максимума текущий не меняется. Например, 35/40 → максимум20 → 20/20 → восстановление максимума40 → 20/40. При исходных 5/40: 5/20 →5/40. Не вводить этим правилом новый нижний предел HP/STA или автоматическое лечение.

Обновление запаса выполнять явной операцией после изменения исходных данных, без `Actor.update` внутри prepare. На один переход — один согласованный результат; повторный рендер/загрузка не повторяет списание. Проверить согласованность с healthState и изменениями встроенных Item/AE, включая эффект по истечении срока. Отдельное лечение/выдача временных значений — самостоятельное действие; простое увеличение потолка/максимума их не выдаёт. «Полнолуние» проверяет запрет суммирования, но этот проект не вводит отдельную систему временных пулов HP под видом настройки максимума.

**Несуммируемый AE:** семейство задаётся `effectTypeId`, не названием или UUID. Если запрет включён, новое назначение того же семейства на Actor заменяет прежнее воздействие и отсчитывает полную длительность заново; два бонуса не остаются. Проверять создание через системное применение эффекта, обычные встроенные документы и актуальные источники transfer. Удаление исходного Item или переписывание шаблона в компедиуме ради запрета суммирования недопустимо. Различать хранимые источники и реально применённый экземпляр; повторное prepare — не повторное назначение.

Замена должна учитывать целостный итог набора эффектов при пересчёте ресурса/допустимой базы. При отказе записи сообщать об ошибке; нельзя считать замену успешной по одному обновлённому листу. Точный вызов нативной операции замены выбрать по проверке Foundry в .009; отдельный межклиентный механизм блокировок автоматически не добавлять. Повтор дозы и токсичность разделены: [TODO](../todo.md) остаётся вне реализации.

## 13. Issue-00036: актуальное решение и сохранённые основания

[Карточка](../issues/potential/issue-00036.md) остаётся potential. Материалы М08/I10/B09 и С13/Б11 перенесены из issue-00332 через TASK-0009; .00039 включила их в общий расчёт. Прежняя развилка сердца **закрыта проектным решением**: штатный эффект BODY÷4 исключается из входа STA, собственный STA÷4 даёт40→10. При настройке без исключения допустим иной результат6. Реализация и локальные проверки .004–.005/.010–.011 выполнены; игровая приёмка остаётся в .013.

Сохраняется установленная причина: начальный effect меняет `stats.*.max`, а calculateStat берёт unmodifiedMax; затем собственный максимум STA может быть перезаписан calculateDerivedStat. Исправление — общий расчёт с отдельными модификаторами и адресными входами; не выключение всех временных BODY/WILL из производных и не hardcode сердца. Контрольные значения SPD8×0.25=2, ×0.5=4; Run6/12 при отсутствии других воздействий. Initial/final, повторная подготовка, выключение/удаление, customStat и сохранённые запасы проверяются отдельно.

Ранее изученные [errata v4, с.8](https://rtalsoriangames.com/wp-content/uploads/2022/03/RTG-WI-WitcherCoreErratav4.pdf) и [The Sage’s Answers, Finale](https://rtalsoriangames.com/2018/10/12/the-sages-answers-finale/) уточняют кровотечение после лечения/деление в предсмертном состоянии, но прямого решения программного порядка сердца там не найдено. Поэтому выбранная конфигурация отмечена как согласованная пользователем, а не выдана за буквальное официальное разъяснение.

Первичные воспроизведения сохранены в карточке 00036 и датированных журналах пофайлового аудита. Исторический проект М08 с ещё не принятыми числами не является конкурирующим текущим алгоритмом: его вопросы заменены настоящим контрактом и подзадачами .004–.005/.010–.013.

Статус: `in-progress` — реализация/локальная проверка .00077 выполнены, игровая приёмка ожидается. Связи: [.014](#task-0010014), [.006](#task-0010006), [00194](../issues/potential/issue-00194.md), [00195](../issues/potential/issue-00195.md). [Назад к плану фиксов](#ui-fixes).

Редактор параметров оформить строками с общими заголовками. Пример компоновки, не новые игровые значения:

| Параметр | База | Действующее | Базовый предел | Действие |
| --- | --- | --- | --- | --- |
| Интеллект | Редактируемое число | Значение с эффектами | Редактируемое число | Повысить параметр |

Полное название параметра, одинаковые компактные числовые поля, выравнивание колонок, достаточное место для кнопки. Действующее значение только отображается. Базовый предел и действующий максимум не смешиваются; в подсказке объяснить влияние модификаторов на итог. Репутации и полям без baseCap не добавлять искусственный потолок. Вычисляемые производные остаются только для чтения; ручной ввод допускается по существующему `isManualDerivedStat`, включая настройки customStat.

Кнопка характеристик получает отдельный ключ ru/en «Повысить параметр» / «Increase attribute»; у навыков остаётся «Повысить навык». Не менять общий перевод skills.levelUp, поскольку у него остаются правильные потребители. Покупка по-прежнему вызывает существующий обработчик, с оплатой, пределами и проверкой ОУ. Ручной ввод и покупка уровня остаются разными действиями.

Редактор навыков привести к той же читаемой структуре: название, база, действующее значение, предел, повышение. Флаги профессии/дополнительного/изученного навыка и сведения о модификаторах оставить в раскрываемых подробностях строки. Сохранить их значения и существующие обработчики; правка соседнего поля не должна записывать prepared-значение как базу.

Оба редактора: высота ограничивается доступным экраном, внутри есть прокрутка; полная подпись поля/кнопки не обрезается. При недостаточной ширине допускается предусмотренный перенос элементов, а не наложение. Оформление изолировано классом modifier-configuration; общие CSS-селекторы Actor не должны превращать диалог в двухколоночную карточку.

Файлы: [WitcherModifiersConfiguration.js](../../module/actor/sheets/configurations/WitcherModifiersConfiguration.js) — контекст/размеры/прокрутка; [edit-stats.hbs](../../templates/sheets/actor/configuration/app/edit-stats.hbs), [stats-block.hbs](../../templates/sheets/actor/configuration/app/partials/stats-block.hbs), [edit-skills.hbs](../../templates/sheets/actor/configuration/app/edit-skills.hbs) — структура строк; [modifier-configuration.css](../../styles/configurations/modifier-configuration.css) — компоновка; [ru.json](../../lang/ru.json), [en.json](../../lang/en.json) — отдельная подпись кнопки и необходимые заголовки. ### TASK-0010.016 — Шапка, пустые значения и предыстория

Статус: `in-progress` — реализация/локальная проверка .00077 выполнены, игровая приёмка ожидается. Связь: отложенная ошибка шапки из [issue-00330](../issues/closed/issue-00330.md#скриншот-ошибка-пустой-шапки-исправление-отложено); закрытая локализационная issue не переоткрывается. [Назад к плану фиксов](#ui-fixes).

**Уточнение пользователя имеет приоритет над первоначальным предложением скрывать пустые части:** все шесть позиций сохраняются в прежнем порядке. Незаполненное значение отображается как `-`; нулевой возраст тоже `-`. Разделитель между позициями — ` - `; совпадение символа разделителя с прочерком принято пользователем. Шапка с заполненными только расой и родиной всё равно содержит шесть позиций. Прочерк — представление пустоты, его не сохранять в Actor вместо пустой строки/числа 0.

| Позиция | Согласованный источник |
| --- | --- |
| Раса | Название Item.race персонажа |
| Профессия | Название Item.profession персонажа |
| Пол | system.gender |
| Возраст | system.general.age; 0 отображается прочерком |
| Родина | Сначала заполненная родина Item.homeland, затем заполненное system.general.homeland, иначе прочерк |
| Социальное положение | system.general.socialStanding; региональная таблица Item.race не подставляется автоматически |

Для родины `other` использовать непустой otherValue; для известного кода — существующий ключ из config.homelands. Имя предмета родины не подменяет его выбранное значение. Пустой предмет родины, в том числе other без текста, не перекрывает заполненную родину предыстории. Пустой/неизвестный код не выводится как WITCHER.*; отображение не изменяет сохранённый источник. Для социального положения использовать соответствие config.socialStanding.

В выпадающие списки предыстории добавить явный вариант «Не указано» со значением пустой строки. При новом Actor форма должна показывать фактическую пустоту вместо first-option «Другое»/«Равенство». Изменение имени, возраста либо другого поля не должно молча записывать other/equal. Согласовать отображение родины в самой предыстории с тем же приоритетом источников; если предмет родины пуст, запасное поле предыстории должно оставаться доступным для заполнения. Не вводить новое автоматическое назначение социального положения или игровое правило.

Файлы: [WitcherCharacterSheet.js](../../module/actor/sheets/WitcherCharacterSheet.js) — подготовка единого представления шапки/родины; [character-header.hbs](../../templates/partials/character-header.hbs) — шесть позиций/разделители/прочерки; [tab-background.hbs](../../templates/partials/character/tab-background.hbs) — пустой выбор и согласованный источник; [ru.json](../../lang/ru.json), [en.json](../../lang/en.json) — подписи при отсутствии подходящего существующего ключа. Для сверки источников: [generalData.js](../../module/data/actor/templates/character/generalData.js), [homelandData.js](../../module/data/item/homelandData.js), [config.js](../../module/setup/config.js); новая схема данных не требуется.
