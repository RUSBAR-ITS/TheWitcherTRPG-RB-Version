## Проблема и результат

Установленный браузер пока только открывает простую страницу. Это не проверяет вход в Foundry, работу WebGL, карточек, настроек, компедиумов или взаимодействие с игровыми документами.

Результат: воспроизводимый стенд, который запускает настоящий Chromium на сервере, входит в заданный мир, выполняет ограниченный сценарий через интерфейс и сохраняет отчёт с доказательствами. Агент может самостоятельно прочитать результат, консоль, сетевые ошибки, скриншоты и при необходимости trace; постоянные ручные скриншоты пользователя для базовых проверок не нужны.

Первый рабочий набор должен быть небольшим: вход/готовность, сцена, карточка Actor, библиотеки, один изменяющий данные сценарий, затем интеграция диагностического снимка. Создание полного набора тестов на всю систему не входит в задачу.

## Требования

### 1. Явная конфигурация и ограничение мира

- Параметры: BASE_URL, EXPECTED_WORLD_ID, EXPECTED_SYSTEM_ID, пользователь, способ передачи пароля, язык, набор модулей/fixtures. Проектное имя мира — `witcher-rb-test`, ID системы — `TheWitcherTRPG-RB-Version`.
- URL брать из фактической установки, с учётом proxy/routePrefix. Ansible сейчас содержит `foundry.rusbar.site`; доступность и текущий маршрут нужно подтвердить после запуска службы, а не считать уже проверенными.
- Перед записью в игровой документ проверять фактические `game.world.id`, `game.system.id` и пользователя в текущем клиенте. При несовпадении завершать сценарий; не выбирать первый мир и не переключать мир через Setup автоматически.
- Браузер не устанавливает/обновляет систему, не меняет конфигурацию службы и не пересобирает действующие packs. Компедиумы К01 отдельно [установлены в .00018](../issues/closed/issue-00331.md#installation); после запуска мира стенд проверит фактическую загрузку библиотек.
- Начальный запуск — один worker, последовательные сценарии, отдельная учётная запись QA. Пользователь не использует её одновременно для ручной игры. Очистка cookies не отменяет записей в мире.

### 2. Вход и готовность

- Headless Chromium с `channel: chromium`, как в успешной пользовательской проверке. Версии Node/Playwright/Chromium/Foundry/системы записываются в отчёт; обновление установленных версий без причины не требуется.
- Вход через настоящую страницу Join под учётной записью мира, не через пароль администратора Setup. Хранение сессии может ускорять повторные запуски; протухшая сессия определяется и обновляется обычным входом.
- Пароли/сессионные cookies не попадают в репозиторий, stdout и отчёт. Файлы auth и локальных секретов исключены из Git, как рекомендует [Playwright](https://playwright.dev/docs/auth). Права назначает пользователь.
- Ожидать конкретные признаки `game.ready`, доступности интерфейса и завершения нужного render. `networkidle` не считать единственным признаком готовности: Foundry держит соединения.
- Проверять ошибки консоли, исключения страницы, requestfailed и HTTP-ответы 4xx/5xx: HTTP 404 не обязан вызывать requestfailed. Запись событий подключать до перехода на страницу; ожидаемые исключения указывать точечно и объяснять.
- Готовность страницы и готовность canvas проверяются отдельно. Если WebGL/сцена не работают, записать конкретную ошибку и renderer; не считать тест сцены пройденным из-за открытия карточки. Возможные параметры программного рендеринга сначала проверить и документировать.

### 3. Настоящие действия интерфейса и доказательства

- Проверяемое пользовательское действие выполнять через интерфейс: открыть лист, нажать кнопку, изменить поле, сохранить форму, раскрыть библиотеку или бросить таблицу.
- `page.evaluate` разрешён для чтения фактического состояния и явно обозначенной подготовки fixtures. Вызов внутреннего обработчика вместо клика не выдавать за проверку UI.
- Использовать устойчивые локаторы доступных имён/подписей, data-action и привязку к нужному окну. Не полагаться на случайный порядок окон и пиксельные координаты там, где есть DOM.
- После изменения формы сверять видимое значение и модель документа, затем повторное открытие/обновление страницы. Простого отсутствия exception недостаточно для подтверждения сохранения.
- Отдельно сохранять результат и ограничения: passed/failed/skipped/blocked. Невыполненный сценарий с отсутствующим миром/модулем не становится passed.

### 4. Fixtures и восстановление

- Минимальные независимые персонаж/монстр, простые предметы и эффекты создаются по небольшим фиксированным данным. Ожидаемые результаты выводятся из согласованного сценария, а не вычисляются тем же кодом системы, который проверяется.
- Для UI-набора нужны чистый Actor и отдельный Actor с Item/эффектом; заготовки дополнить привязанным и непривязанным токенами. Чистый Actor позволяет отличать базовую проблему листа от влияния эффекта.
- Подготовка может использовать штатный API документов Foundry; она отмечается отдельно от UI-действий. Редактировать LevelDB мира напрямую нельзя.
- Созданные документы помечаются UUID/runId/собственным флагом стенда и помещаются в тестовую папку. Удалять только объекты, достоверно созданные текущим запуском, после повторной проверки мира; не чистить весь мир по названию папки.
- Если сценарий меняет настройку, сохранять исходное значение и восстанавливать его; обработать падение/прерывание и список оставшихся документов. Не запускать автоматический сброс чужих сессий или игровых данных.
- До первого изменяющего данные прогона иметь понятный способ восстановления тестового мира. Резервная копия всего мира делается при корректно остановленном мире/службе; очистка fixtures и восстановление резервной копии — разные операции.

### 5. Артефакты и связь с диагностикой

На запуск: runId, времена, URL/worldId/systemId, фактические версии, язык/модули, пользователь без секрета, перечень сценариев и итоговые статусы. При ошибке — скриншот, console/pageerror, сведения о неуспешных запросах и trace. Формат и лимиты хранения описать в README; снимки/trace могут содержать данные тестового мира.

Не включать тяжёлые видео и полные trace во все успешные повторные прогоны без потребности. Для точечного воспроизведения предусмотреть включение подробного trace. [Trace Viewer](https://playwright.dev/docs/trace-viewer) позволяет сопоставлять действия, состояние страницы и сеть.

После готовности [TASK-0007](task-0007-witcher-diagnostics.md) стенд вызывает её API для выбранного тестового Actor и прикладывает snapshotId/результат доставки. При браузерном отказе, когда API недоступно, сохраняет собственные артефакты. Нельзя требовать диагностический модуль для базового входа в мир: это создало бы круговую зависимость при его разработке.

## Этапы реализации

1. Уточнить URL, ID отдельного мира, QA-пользователя, доступ и начальные настройки. Сохранить существующие package.json/lock; создать структуру стенда и конфигурационные примеры.

3. Подготовить минимальные fixtures через штатный API, выполнить P03–P06; проверить cleanup и сохранность чужих документов.
4. Добавить P08 отдельным профилем обычного игрока. Проверить повторный запуск и протухшую сессию.
5. После готовности модуля подключить P07, не меняя базовую схему входа и независимые тесты.
6. Записать команды и фактические результаты, ограничения renderer/модулей/ролей; обновить документацию. Не расширять набор до полного регресса системы автоматически.
