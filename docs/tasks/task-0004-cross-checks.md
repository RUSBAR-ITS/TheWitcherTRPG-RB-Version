## Границы и методика

1. Охват — все 615 файлов актуального реестра и все 329 исходных issues с учётом последующих согласованно зарегистрированных наблюдений. docs/ изучается как материал проверки, не добавляется в реестр исходников. assets/, .github/, .git/, packs/, служебные пути и шесть других языков остаются исключёнными по прежним правилам.
2. Проверяется техническая работа кода и экспортов. Соответствие рулбукам, изменение чисел/правил, создание нового контента и рефакторинг движка сюда не входят.
3. Сверять карточку с исходником, затем оба конца связи. Отличать импорт, объявление/регистрацию, найденное место возможного вызова и действительно выполненный маршрут. Наличие строки, поля или UUID не доказывает достижимость действия.
4. Для данных прослеживать source → очистку/миграцию → prepared → аргументы/модель сообщения → потребителя → запрос обновления. Различать вычисление, мутацию в памяти, вызов записи и завершённое сохранение.
5. Для нового утверждения о поведении использовать настоящее определение метода/модели и фактически установленное ядро. Изолированные сценарии через stdin допустимы с явно описанными фасадами; отдельный стенд и тестовые файлы не создаются.
6. Новый запуск нужен при противоречии, изменённой зависимости, неподтверждённой границе или вопросе, на который прежний сценарий не отвечал. Повтор неизменённых проверок не нужен только ради счётчика; применение прежнего доказательства всегда отмечается с его датой, входами и пределами.
7. Полный клиентский lifecycle, браузер, мир/БД и несколько клиентов не подтверждаются фасадами. Не выполнять install/build/compile/extract, запуск службы/мира, миграцию или запись игровых документов в рамках этой документальной задачи.
8. Исправлять только доказанные расхождения описаний. Регистрация обнаруженных технических проблем в potential уже входит в согласованные требования TASK-0004 и исследования; перед записью исключить дубль по полным карточкам и сообщить наблюдение пользователю. Подтверждение пользователем, перевод в open/closed, объединение/удаление issue и исправление системы требуют отдельного решения.
9. Исходники, данные, права и владельцы сохраняются; существующие документы редактируются с сохранением метаданных доступа. Согласованные требования [репозитория](../rules/README.md) продолжают действовать.

## Порядок выполнения и основная принадлежность файлов

.001 создаёт общий срез и матрицы. .002–.017 выполняются последовательно по предметным процессам с указанными зависимостями. .018 сопоставляет все результаты и готовит завершение родителя. Каждый внутренний этап заканчивается записью проверки; длинные блоки можно продолжать с сохранённой позиции.

У каждого исходника одна основная подзадача, отвечающая за содержательную сверку его карточки. Определения и потребители из других блоков проверяются также как смежные связи. Для них общий структурный проход сочетается с отдельной проверкой цепочек и исключений. Остальные блоки также разделены на внутренние этапы; основной объём не задаёт число новых тестов.

Для проблемы основной блок определяется по месту причины/проявления, смежные блоки — по затронутым процессам. .001 готовит распределение по реквизитам и локализации, включая поздние уточнения при неясности; предметный блок обязан прочитать назначенные issues целиком. .018 проверяет результаты всех строк и полностью разбирает оставшиеся спорные/неназначенные случаи. Так все 329 карточек получают содержательный результат; автоматический сбор ссылок не считается их проверкой.

### Матрица связей и процессов

| Поле строки | Содержание |
| --- | --- |
| Определение → использование | Оба файла, точная сущность/поле/обработчик и место обращения |

Число связей устанавливается по фактическому коду, а не заранее. Реестр отражает найденные связи; отсутствие найденного внешнего макроса не доказывает отсутствия возможных внешних потребителей. Для многошагового процесса записывать вход, цепочку, выход, ранние барьеры и условия последующих шагов.

### Матрица issues

| Поле строки | Содержание |
| --- | --- |
| ID / текущий статус | Ссылка на неизменяемый ID и фактический каталог potential/open/closed |
| Основной / смежные блоки | Ответственный за полное чтение и связанные процессы |
| Основание и локализация | Суть причины/проявления, точные файлы/сущности |
| Технический результат сверки | Основание сохраняется / описание уточнено / вероятный или установленный дубль / недостаточно доказательств; с пояснением |
| Связанные issues | Одна причина, разные причины похожего симптома, последовательные барьеры либо независимые наблюдения |
| Доказательства / ограничения | Текущая версия и применимые протоколы, поздние уточнения и отозванные выводы |

Технический результат сверки не является пользовательским подтверждением и не меняет каталог issue. Известный дубль 00029/00200 учитывается явно; число карточек не объявляется числом независимых дефектов.

### Неразрешённые вопросы

Для каждого: файл/сущность, точный вопрос, прежнее доказательство, чего оно не покрывает, ответственный блок, достаточная следующая проверка и влияние на текущий вывод. По итогам .018 не должно оставаться безадресного «проверить после будущей порции». Вопрос либо получает ответ, либо остаётся с конкретной внешней/недоступной границей; невыполненную доступную проверку нельзя просто переименовать ограничением.

### Протокол подзадачи

Запись TASK-0004.NNN в review-log.md содержит дату/версию/рабочее дерево, обработанные файлы/связи/issues, прочитанные определения, новые сценарии и их входы, команды или описание воспроизводимого запуска, результат и пределы. Для фасадов указать заменённые операции. Отдельно перечислить уточнённые документы, применённые старые доказательства, открытые вопросы и проверку сохранности.
