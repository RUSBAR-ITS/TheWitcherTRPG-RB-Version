## Связи и порядок проверки

1. Сопоставить ID системы, пути ресурсов, типы документов и packs в system.json с регистраторами, константами путей и точкой входа. Для типов выделить объявление, класс данных, лист и доступность создания.
2. Проследить init/setup/ready, Hooks и порядок настройки CONFIG/game. Проверить, в какой момент существуют данные для индексирования компедиумов и подключения внешних интеграций.
3. Проверить соответствие ключей queries/socketHook зарегистрированным обработчикам, аргументам и возвращаемым значениям. Передать предметные проверки доставки в .011, а результаты обработки областей — в .009.
4. Сопоставить helpers/preload/зарегистрированные PARTS с путями HBS; базовые CSS — с подключением и фактическими корнями шаблонов. Подробные состояния представления сверяются в .016.
5. Сопоставить package.json/build.json/compile/extract с каталогами экспортов и манифестом. Статически установить побочные действия CLI, не выполнять сборку или извлечение.
6. Для внешнего API определить установленную версию и проверить конкретное определение. Старое имя API или комментарий не считать доказательством отказа без проверки доступности и контракта.

## Внутренние этапы

1. Манифест и типы → регистрация моделей/листов.
2. Hooks, helpers и ресурсы → доступность обработчика.
3. Настройки, packs и CLI → передача внешних связей.

После каждого внутреннего этапа записать проверенные файлы и связи, выводы, использованные старые доказательства и новые проверки. Если поздний потребитель меняет понимание ранее разобранного источника, уточнить обе карточки и соответствующую строку общей матрицы. Следующий номер задачи сам по себе не является программной зависимостью.

## Контрольные случаи

- Отсутствующий тип или обработчик: проследить первую границу, на которой компонент становится недоступен.
- Пустой/отсутствующий пакет и момент ready: отделить декларированный пакет от индекса действующего мира.
- Ожидание query/socket: результат метода и завершение зависимой операции фиксировать отдельно.

Это план проверки, а не заранее установленный результат. Для нового исполнения использовать настоящую модель/метод и фактически проверенную версию ядра; ожидание обосновывать контрактом вызывающей стороны. Где достаточно повторного чтения неизменённого кода и применимого протокола, указать это явно. При недоступной границе сузить вывод и записать точный непроверенный вопрос.
