## Проблема и результат

Серверные логи Foundry не дают полного контекста действий браузера и подготовленных данных персонажа. Сейчас для Witcher нет подключённого инструмента, позволяющего получить такой контекст на сервере одной командой. Для другой системы уже существует клиентский сбор событий с доставкой в отдельную Node-службу.

Результат: самостоятельный диагностический модуль для `TheWitcherTRPG-RB-Version`. Пользователь выбирает персонажа/токен, выполняет одну команду и получает ID отчёта. Отчёт появляется на диске сервера и доступен для последующего анализа агентом. Снимок работает и при выключенном непрерывном журнале. Он показывает состояние в момент снятия; восстановление прежнего состояния до ошибки без заранее собранной истории не обещается.

Пример: после изменения эффекта персонаж показывает неожиданную скорость. Снимок должен позволить сопоставить исходные поля Actor, подготовленные характеристики, вложенные Items, собственные и предметные эффекты, состояния включения/подавления и настройки расчёта. Сам диагностический модуль не исправляет скорость и не воспроизводит вместо системы её формулы.

## Требования

### 1. Выделение самостоятельного модуля

- Клонировать диагностическую часть, сохранив сведения о её происхождении. Не переносить переводы, изменения листов, механики или хуки WoD, не относящиеся к диагностике.
- Не подключать исходный модуль WoD к миру Witcher и не изменять его код/службу при реализации новой задачи.
- Поддерживать текущий Foundry 14 и текущий ID форка. Совместимость со старыми системами и миграциями в задачу не входит.
- Предлагаемые имя и место: `witcher-trpg-diagnostics`, каталог `/var/lib/foundryvtt/Data/modules/witcher-trpg-diagnostics`. Это проектное имя до реализации.
- Предлагаемый лог-каталог: `/var/lib/foundryvtt/Logs/witcher-trpg-diagnostics`. Сведения о мире, пользователе и сессии входят в каждую запись; размещение и права определяются при согласовании установки.

### 2. Снимок одной командой

Предлагаемый публичный контракт:

```js
await game.modules.get("witcher-trpg-diagnostics").api.captureSnapshot({
  actorUuid: "Actor.…",
  reason: "Неверная скорость после включения эффекта"
});
```

Предусмотреть вызов без UUID для ровно одного управляемого токена и короткий макрос для панели. При отсутствии/множественном выборе вернуть понятное объяснение, а не угадывать Actor. Явный `tokenUuid` должен выбирать Actor соответствующего токена, включая непривязанного; нельзя молча подменять его исходным Actor из каталога. Окончательные имена API и доступ из заголовка карточки уточняются при реализации; отдельный большой интерфейс не требуется.

Команда возвращает структурированный результат: snapshotId, состояние сбора, состояние доставки/сохранения, сведения о неполных разделах. Успех записи на сервере показывается после подтверждения сборщика. При недоступности сборщика собранный снимок остаётся доступен локально для скачивания; отказ доставки не объявляется успехом серверной записи.

| Раздел снимка | Обязательные данные и различия |
| --- | --- |
| Контекст | schemaVersion, snapshotId, sessionId, время начала/окончания, причина, worldId, userId/роль, язык, Foundry/system/module версии, сцена и tokenUuid при наличии |
| Actor | UUID, тип, исходные сериализованные поля и отдельный раздел текущих подготовленных значений system; характеристики, навыки, производные показатели, ресурсы и боевые поля |
| Токен | UUID/sceneId, actorLink, связь с базовым Actor и фактический Actor токена; отсутствие сцены/выбора отражается явно |
| Items | UUID/ID, тип, источник/родитель, исходные и относящиеся к диагностике подготовленные поля; equipped/isActive и травматические treatment/location/followUp там, где они есть |
| ActiveEffect | Эффекты самого Actor и Items с владельцами, disabled/transfer/statuses, origin, duration и прочитанными состояниями active/suppressed/expired; изменения в фактическом формате Foundry 14, включая `system.changes` и phase, а также специфические поля Witcher |
| Применимость | Отдельно собственные эффекты, эффекты предметов и набор, который текущий Actor считает применимым. Ошибку чтения getter записывать как ошибку раздела, не заменять значением false |
| Настройки | Зарегистрированные настройки Witcher и диагностического модуля; относящиеся к сценарию core/внешние настройки по явному списку. Для каждой указывать namespace/key, scope, доступное эффективное значение или причину недоступности |
| Модули | ID, версия, включённость, сведения о текущем наборе расширений; содержимое иных модулей не выгружается целиком |
| Компедиумы | Объявленные пакеты и реально присутствующие `game.packs`, collection/type/package, доступность/locked, состояние индекса, известные поля/размер индекса и число документов в клиентском кэше — отдельно |
| Полнота | Статус каждого раздела: собран / недоступен / ошибка / не загружен / усечён; причины, лимиты и число пропущенных элементов, если известно |

В базовом снимке не загружать автоматически содержимое всех компедиумов. Пустой кэш документов или не загруженный индекс не означает пустую БД. Отдельный режим явной проверки выбранного пакета может запросить индекс/один документ с фиксацией результата и времени; это чтение, не запись пакета.

Снимок сериализует текущие данные без вызова `update`, `updateSource`, принудительного `prepareData/reset` или повторного применения эффектов. Пока сбор идёт, мир может меняться: отмечать границы времени и наблюдённые обновления, не обещать атомарный снимок серверной БД. Он отражает доступное конкретному клиенту состояние, а не данные всех игроков.

### 3. Базовый журнал событий

- Переключатель сбора; снимок по запросу работает независимо от него.
- Ошибки браузера/Promise и сообщения console с сохранением исходного поведения console; события открытия/закрытия окон, создания/обновления/удаления документов и выбранные действия интерфейса.
- Сохранять UUID документа, идентификатор окна/действия, изменения полей, клиентский порядковый номер, sessionId, клиентское и серверное время. Инициатора обновления и клиента-наблюдателя различать, чтобы одинаковые сетевые события не считать несколькими действиями пользователя.
- Предварительный запрос изменения и подтверждённое обновление отмечать разными типами событий. Временная близость клика и обновления не доказывает причинную связь; надёжную связь указывать только при наличии соответствующего идентификатора/контекста.
- Очередь ограничена; доставка пакетная и не задерживает игровые действия. Счётчики пропуска, усечения и ошибок доставки доступны в диагностике. Не маскировать потерю событий.
- Подписки не дублируются после повторной инициализации. При выключении прекращается запись и снимаются собственные обработчики/обёртки, где это предусмотрено; чужие обработчики сохраняются.
- Полный трассировщик всех функций, перехват всех сетевых payload и постоянная запись полного Actor на каждый клик не входят в первую версию.

### 4. Запись и эксплуатация

- JSON для целого снимка, JSONL для событий; форматы имеют версию. Сборщик подтверждает ID принятого отчёта; агент должен иметь возможность прочитать именно этот отчёт после подтверждения.
- Отдельная Node-служба за существующим HTTPS reverse proxy. Конкретные endpoint/порт/проверку допуска согласовать при реализации. Порт 30120 уже занят службой WoD; не подменять её.
- Ограничить размер запроса/снимка, частоту и объём хранения. Усечение диагностических данных всегда обозначать. Предусмотреть понятную ротацию/срок хранения без очистки чужих журналов.
- Не выгружать пароли, cookies, токены и произвольное содержимое всех настроек. Путь файла строит сервер; сырые значения метаданных не могут стать произвольным путём, включая `.`/`..`.
- Не копировать бесконтрольный endpoint очистки и wildcard CORS исходного сборщика. Проверка server-side допуска к отправке не заменяется присланным клиентом `isGM` или одним Origin. Это адресные требования к улучшению имеющейся реализации; точный способ будет зафиксирован до развёртывания.
- Модуль читает только доступные текущему пользователю документы. Снимок чужого Actor без разрешения не должен становиться способом обхода Foundry ownership.
- Развёртывание описать воспроизводимо с учётом существующего Ansible. Пользователь управляет правами/владельцами; агент не меняет их и не расширяет доступ автоматически.

## Границы и зависимости

Требуется диагностический инструмент, а не рефакторинг игровой системы. Ошибки, наблюдаемые инструментом, не исправляются скрыто в его коде. Существующие [issue-00320](../issues/potential/issue-00320.md), [issue-00328](../issues/potential/issue-00328.md), [issue-00036](../issues/potential/issue-00036.md) остаются отдельными механиками.

До начала кода определить размещение исходников/порядок версионирования отдельного модуля. Создание удалённого репозитория и публикация автоматически не входят в задачу. Исходный WoD-модуль остаётся контрольной основой, а не зависимостью времени исполнения.

[Браузерный стенд TASK-0008](task-0008-foundry-browser-tests.md) позднее проверит команду снимка и сохранит snapshotId вместе с тестовым отчётом. Нужны две независимые приёмки: воспроизведение в браузере пользователя → запись сборщиком и автоматический сценарий в браузере агента → запись сборщиком. Работа одного клиента не доказывает подключение другого.

## Этапы реализации

1. Зафиксировать используемые исходники WoD, выделить диагностические компоненты, определить собственный namespace и формат отчёта. Согласовать конкретную установку службы/доступ, не запускать старый установщик целиком.
2. Сделать сбор снимка в памяти, явный выбор Actor/Token и сериализацию с отчётом о полноте; добавить адаптер текущих моделей Witcher.
3. Подключить единый транспорт снимков/событий и отдельный сборщик; проверить подтверждение записи, отказ и локальное сохранение снимка.
4. Добавить базовые наблюдатели событий и настройки en/ru; проверить выключение, повторное подключение и отсутствие изменений игровых документов.
5. Подготовить инструкции и конфигурации для развёртывания, выполнить согласованную установку. Проверить реальный запрос из браузера через HTTPS и доступ агента к полученному файлу.
6. Пройти контрольные сценарии в тестовом мире, обновить документы по фактической реализации. Сведения о выполнении записать здесь; наблюдения не превращать в новые задачи без согласования.

## Критерии приёмки и проверки

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Снимок при выключенном журнале | Одна команда → отчёт на диске, читаемый агентом, и подтверждённый snapshotId |
| Actor без Items/эффектов | Валидные пустые разделы, не ошибка сбора |
| World Actor, привязанный и непривязанный токен | Выбран правильный объект; UUID/родитель/подготовленные данные не смешаны |
| Два токена выбраны / ни одного | Понятный ответ; произвольный персонаж не выбран |
| Эффект выключен/подавлен/истёк, Item не экипирован | Отдельно записаны фактические исходные и вычисленные состояния; ошибка getter заметна |
| Новый системный changes/phase | Реальный формат Foundry 14 отражён в снимке; нет предположения, что старый JSON компедиума равен текущей модели |
| Пустой / не загруженный / недоступный пакет | Состояния различаются; нет автоматического вывода «контент потерян» |
| Сборщик недоступен / запрос слишком велик | Игровое действие продолжает работать; ошибка доставки/полноты видна, снимок можно сохранить локально |
| Повторный запуск/выключение журнала | Один обработчик на событие; отсутствует двойная запись через console и транспорт |
| Изолированный вызов снимка | Нет вызовов записи Actor/Item/ActiveEffect и нет изменений сравниваемых исходных данных |
| Обычный игрок | Нет обхода ownership; недоступность разделов отражена явно |

## Открытые вопросы перед реализацией

- Подтвердить предложенное имя/размещение исходников отдельного модуля; наличие отдельного Git-репозитория не предполагается автоматически.
