## Порядок разбора

1. Для каждого CSS установить @import-путь от system.json, порядок относительно глобальных и родственных правил; составить перечень всех селекторов и declarations по смысловым группам.
2. Разобрать общие вкладки биографии, инвентаря и навыков, включая псевдоклассы, раскрытие details и скрытые/активные состояния; найти конкретные HBS и JS.
3. Полностью разобрать character-header.css и character/sheet.css: не ограничиваться первыми селекторами или названием файла; сопоставить все внутренние группы с зарегистрированными листами.
4. Разобрать семь файлов монстра, разделив старый полный шаблон и текущие PARTS; сопоставить общий и специализированный CSS.
5. Сверить специфичность, вложенность, наследование и порядок общих/частных правил; у каждого предполагаемого пересечения указать селекторы, применимую разметку и пределы проверки.
6. После каждого внутреннего блока (общие вкладки, персонаж, монстр) сверить собственный перечень правил и найденные HBS/JS; затем выполнить общую сверку всех 13 CSS.

- Все 13 файлов прочитаны целиком; таблицы селекторов/групп не пропускают остаток большого файла. Нет сведения всего CSS к одной строке «оформление листа».

- Общие селекторы вне корня листа, вложенные правила и псевдоэлементы; фактическое совпадение на доступном HTML и влияние порядка @import.

После содержательного разбора сверить карточки с исходниками, определения и потребителей — между собой, реестр — с точным составом порции. Проверки должны устанавливать наблюдаемый результат; ожидаемое значение не вычислять проверяемой функцией.

Для CSS перечислять все селекторы и существенные группы declarations, подключения, классы-потребители и пересечения каскада. Отсутствие функций не освобождает от описания сущностей и зависимостей. Совпадение селектора, доступность ресурса и фактическую отрисовку различать.

При использовании Foundry фиксировать фактическую версию и источник. Различать настоящий код, локальные фасады, браузер и серверную запись. Проверять очистку DataModel на границе производителя и потребителя; запрос update не объявлять сохранённым результатом. Если ранняя ошибка блокирует маршрут, явно ограничить отдельную проверку следующей стадии. Для переводов учитывать штатные expandObject и fallback.

Создание стенда, сборка, изменение исходников/игровых данных и исправление выявленных проблем не входят в задачу. Полный игровой процесс не считается проверенным по статическому чтению или подменённым API.
